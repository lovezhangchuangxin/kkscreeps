# 开放领域定义与玩家投影

本文细化 [ADR-014](../decisions/ADR-014-contribution-plane.md) 和 [Mod 设计](mod-system.md)，作为[贡献平面计划](../plans/mod-plane-batches.md) B 阶段的实施依据。对象、字段、意图、规则与玩家投影共用启动时冻结的定义；实现可以分步接入，但不能各自维护类型目录和字段权限。

B.2 已把 link 有效规则接入放置、建造、结算、配额、伤害与玩家常量，并落地槽执行器（Native/Chained、wrap-next 语义、装配拒绝）；实现与验证边界见 [B.2 接线记录](../research/notes/b2-link-wiring-2026-10-02.md)。B.3 已落地对象级扩展字段全链（挂载声明、扩展目录、写入门校验、发布前引用一致、投影按 Public/Owner/ServerOnly 裁切），见 [B.3 记录](../research/notes/b3-extension-fields-2026-10-02.md)。B.4 已落地 KKPV v1 编解码原型与同源桥（见 [B.4 记录](../research/notes/b4-kkpv-prototype-2026-10-02.md)）。

本文定义 B 阶段的目标接口与二进制布局。B.1 已建立独立的 `kk-mod-api` 描述、校验与冻结入口，尚未接入生产引擎；具体实现边界见 [crate 说明](../../crates/kk-mod-api/README.md)。设计的源码核查基于 `0fa131a`；现有执行与快照机制见 [tick 契约](../architecture/tick-contract.md)与[快照契约](../architecture/snapshot-contract.md)。可信 JS 玩法 VM、Mod 加载及玩家模块安装由 C 阶段接入，持久化迁移与崩溃恢复由 E 阶段完成。

## 1. 当前机制与首个接入对象

当前玩家数据由 `World::world_json_for_viewer` 生成，运行协调器逐玩家投影，再交给沙箱 prelude 装配。`kk-schema` 的房间快照是权威对象的顺序编码，并非经过权限裁切的玩家共享缓冲区。查询快照另有格式，不能直接把管理查询输出当作玩家数据协议。

| 环节 | 现有入口 | 需要解决的问题 |
|---|---|---|
| 类型与字段 | `kk-schema/src/room.rs` 的 `RoomObject`、`GenericObj` | 内建与扩展共用稳定键和字段描述；不能将任意 Generic JSON 原样公开 |
| 玩家意图 | `kk-engine/src/intent.rs` 的 `Action`、清洗器 | 保留内建编码优化，同时接受已注册动作；身份由宿主绑定 |
| 结构结算 | `settle/structures.rs`、`settle/economy.rs` | 类型分派、默认处理器与规则数据有明确的替换入口 |
| 初始化与建造 | `kk-world/src/place/place_structure.rs`、`settle/creep/build.rs` | 有效规则贯穿创建、容量与结算 |
| 玩家 API | `kk-runner/src/prelude/30_game/structures_spawn.js` 等 | 预检、常量、Store、包装器与结算使用同一版本的定义 |
| 可见性 | `kk-world/src/world_json.rs`、`kk-runtime/src/embed.rs` | 对象权限、字段权限和全局集合分别处理；公开部分才可共享 |

首个完整接入家族选 **link**。它涵盖初始化、Store、控制器配额、玩家预检、动作、双对象更新、事件和逐 tick 冷却，能够验证定义是否贯穿调用链。rampart 的动作较小，但完整家族还涉及移动、寻路、受伤遮挡与衰减，适合作为第二个家族。

link 当前是 `RoomObject::Generic`，没有专用 Rust Link 变体。第一步保留权威表示，通过内建字段适配器接入描述与处理器；不同时更换快照变体，避免将行为迁移与存储升级混在一起。

必须保留的行为包括：

- 玩家方法 `transferEnergy` 记录的是动作 `transfer`。预检顺序影响返回码；当前 API 将零 amount 按缺省量处理，不能通过统一参数转换改变。
- 玩家 API 拒绝自身作为目标，但原始意图结算已有自转移行为及测试。两层不能合并成一个更严格的校验器。
- 普通转移先按目标余量裁切数量，再按 `ceil(amount * loss_ratio)` 计算损耗；源扣除总量，目标增加扣除损耗后的量，事件记录总量。
- 自转移只扣损耗，距离为零；不能用两份旧数据分别回写同一对象。冷却先由动作增加，再在同轮对象 tick 中减一。
- 结算的 Generic 归属门允许无主对象进入，玩家 API 的归属检查另有顺序。迁移先保持行为，发现差异须另列修复和回归证据。

对应测试位于 `kk-engine/tests/settle_tests/m2b_structure_actions_family.rs` 和 `m2b_structure_decay_family.rs`。默认贡献迁移不能借机“整理”这些语义。

## 2. 冻结定义与稳定身份

新增纯 Rust 数据层 `kk-mod-api`，提供描述、合并校验与冻结结果，不依赖 V8、引擎 `Working` 或运行协调器。以下名称表示接口职责，Rust 签名在对应切片中确定。

| 定义 | 必需信息 | 冻结结果 |
|---|---|---|
| `ObjectTypeDescriptor` | 稳定类型键、版本、归属/位置模型、字段、能力、生命周期入口 | 类型句柄、字段布局与索引 |
| `FieldDescriptor` | 稳定字段键、值类型、缺省/缺失/null、限额、权限、读写入口 | 字段句柄、编码与投影规则 |
| `IntentDescriptor` | 动作键、作用域、接收者、参数、身份要求、合并方式、阶段 | 清洗与派发表、冲突关系 |
| `RuleDescriptor` | 规则键、数值类型、范围、默认值、消费者 | 平坦的 `EffectiveRules` |
| `HandlerDescriptor` | 处理器键、槽位、before/wrap/replace/after、依赖、实现引用 | 预编排执行计划 |
| `ProjectionPlan` | 类型/字段目录、对象与字段权限、包装器和查询索引 | JSON 与二进制共用的计划 |

稳定键使用 `namespace:name`，内建使用保留命名空间 `builtin`。字段身份包含所属类型或扩展宿主，不能只用短字段名。重复定义、未知引用、依赖环、版本不匹配在启动时拒绝，报错包含来源和冲突键。

紧凑整数句柄在冻结时按稳定键确定，用于本次计划的数组索引。它们不写入持久化身份，也不复用 `RoomObject` 的编码 tag。增删定义可能改变句柄，字节视图必须带计划指纹并拒绝混用。自定义 FIND/LOOK 数字映射作为玩家 ABI 随计划记录，不占用已有常量，不作为跨版本永久身份。

计划指纹采用 SHA-256，对描述、有效规则、执行顺序、权限、布局版本以及 Mod 源码/配置和玩家模块摘要进行规范编码；函数指针地址不参与。相同输入以不同注册顺序提交，应得到相同计划。启动后禁止改变定义；B 阶段不提供热更新。

内建默认值可被一个显式规则贡献覆盖；多个贡献覆盖同一规则时默认报冲突，只有服主配置明确选择来源后才能冻结。数值规则不使用 handler 的 wrap 顺序来隐式决定赢家。缺省值、版本和权限同样不能由注册先后改变。

能力声明须列出实际消费者，如 Store、建造、阻挡、伤害目标和 FIND 分类。不能只给包装器加方法，而让结算仍按旧白名单拒绝。未接入的能力在启动校验或功能范围中明确拒绝，不静默降级。

## 3. 有效规则与权威状态

`EffectiveRules` 冻结为只读 struct 和数组，结算通过已解析句柄读取，不逐动作解析规则 JSON 或查命名空间字符串。默认值来自内建贡献；已迁移的消费者不能直接绕回 `kk_core::constants`。

link 首组规则包括 hits/hitsMax、energy 容量、建造成本、RCL 配额、冷却系数和损耗率。接入覆盖放置默认值、建造落成、Store 容量、`isActive`、动作预检、权威转移、冷却 tick、玩家常量与投影。显式放置字段的覆盖行为仍遵守现有放置契约，不能用默认容量覆盖测试输入。

启动校验数值宽度、有限浮点、范围和关联约束。默认 native link 处理器要求容量/冷却非负、损耗率在 0..1，乘法及转换不得溢出。超出模型的玩法须替换相关行为和数据表示，不能截断后继续运行。区分表示安全与默认玩法限制：替换处理器后保留表示安全检查，不隐藏地再次执行被替换的 vanilla 条件。

`ExtensionState` 保存扩展对象及对象、房间、玩家、世界上的扩展字段。内建字段由适配器直接访问权威对象，不能在扩展表再保存一份 energy 或 cooldown。扩展值支持 bool、定宽整数、有限浮点、字符串、引用、枚举、数组、有界映射和记录；字节数、元素数、嵌套深度与总载荷均有显式限额，不用无界 JSON 作为最终模型。

扩展更新、创建/删除/跨房及索引变化纳入候选事务。发布前校验引用和索引一致性，失败丢弃候选；删除对象不留下字段或目录项。计划与候选版本一起校验，不能用新定义解释旧候选。

## 4. 意图与处理器入口

清洗由宿主绑定玩家身份，参数不能覆盖身份。未知动作仍丢弃，已注册动作按描述校验作用域、接收者和载荷限额。vanilla 的 parseInt 前缀等转换保留原路径，不能用严格 schema 全面替换。扩展动作明确声明转换方式。

默认同一玩家、对象、动作保留最后一次调用；队列动作声明数量上限与确定顺序。房间、玩家、世界动作单独声明作用域。压制关系在冻结时生成执行表，保持默认“指令是否存在”而非“是否成功”的压制语义。

Record 载荷分别声明成员和可省略成员，缺失与 null 使用不同约束。link 的目标 ID 与 amount 必需存在，resourceType 可省略或为 null；原生结算仍按 energy 转移，不因补充 schema 引入额外资源类型门。

玩家预检决定返回码及是否记录；权威处理器重新检查当前候选。两层共用规则数据，但不能合成忽略顺序和竞态的总校验函数。宿主始终检查身份、载荷和计划一致性；可替换的归属、容量、距离等玩法条件由对应入口负责，不在外层重复埋入 vanilla 否决条件。

首个具名动作入口为 `builtin:link.transfer` 和 `builtin:link.tick`；初始化、容量和配额读取同一规则目录。更广的移动、伤害、建造流程仍按原链路运行，能力消费者接入属于后续家族与 D 阶段；不能声称 link 迁移已经开放全部结构规则。

入口编译为 `Native` 或 `Chained`。无附加处理器时直接调用 native，有贡献时执行预编排链，默认新增成本须测量。链沿用 Mod 设计：before 按依赖顺序，wrap 从外到内，中心为唯一 replace 或 native，成功后的 after 逆序。wrap 不调用 next 即截止后续；next 至多一次，异步返回、重复调用、非法补丁或异常使候选失败。多个 replace 默认报冲突，不采用加载顺序覆盖。

阶段仍由引擎控制：对象动作、移动仲裁、对象 tick、市场、校验、发布。依赖只能安排同一合法阶段内的处理器，不能把 after 放到发布之后；冷却递减不能移到转移之前。

B 阶段先接 Rust 默认处理器和测试链，C 再接 JS 引用。`kk-mod-api` 只存实现标识，native 表由引擎装配，JS 函数留在 VM。现有 `Working` 持有房间可变借用，不能跨 JS 回调保留：调用前结束借用，传 ID 和候选句柄，校验回调补丁，next 前重新短借用并读最新状态。禁止 unsafe 指针或生命周期转换。

## 5. 玩家投影与权限

投影是已提交版本的授权视图，不是权威快照的 getter 集合。`ProjectionPlan` 同时驱动 JSON 参考编码与二进制编码，两者不能另写权限表。

基础字段权限为对象可见后公开、仅授权 owner、仅服务器；条件权限使用明确的投影判定入口并进入计划指纹。对象可见性先于字段权限：字段公开不意味着可以从不可见房间取出对象。

公开块只含对受众都可见的对象与字段；私有 overlay 在宿主授权后按玩家生成，绑定身份、计划和代际。server-only 不进入玩家块；仅 owner 可见的对象也不能出现在公共目录。条件权限影响受众时分组缓存或用私有块，不能为“每房编码一次”牺牲权限。

世界级 `PlayerView` 固定 tick、generation 和 plan，保存已授权的房间句柄、可见房间集合、全局 ID 到授权对象所在块的路由及私有通道。不可见房间中的己方旗/工地使用独立私有集合，不为取得它们发放全房句柄。目录只包含授权对象，不能通过全量 ID 索引泄露其他房间内容。预算与代码修订随 RunJob 绑定该视图，不由房间块决定。

保持现有语义：己方旗与工地可进入全局集合，但不授予视野或创建 `Game.rooms`；他人的旗排除，敌方普通对象在可见房可出现；当前所有已注册房间地形仍提供。events、市场、GCL、CPU 预算、RawMemory 走对应授权通道，不能因不在房间字段目录而丢失或全量公开。

Generic 未知字段不自动获得公共权限。已支持类型逐字段核对玩家用途，先建立保持现有可见行为的适配器，再裁切内部字段；管理查询可保留完整数据。

包装器保存 ID 与查看者上下文。本轮读取固定同一世界版本，跨轮重新定位，不缓存裸 row/offset。删除、跨房、失去视野及权限撤回按现有 API 和兼容用例锁定，不自定 undefined/null/异常。字符串、body、Store 按代际缓存，FIND/LOOK 和枚举使用生成索引。

## 6. 二进制布局与存活期

玩家协议独立命名为 `KKPV`，首个原型版本为 1，不复用权威快照版本或 tag，也不构成持久化格式冻结。布局从一个 schema 生成 Rust 与沙箱定义；原型调整须同步更新版本和双方实现。

整数小端，头部 160 字节，所有范围相对整块起点：

| 字段 | 宽度（字节） | 含义 |
|---|---|---|
| magic、version、flags | 4、2、2 | KKPV、版本、公开或私有块 |
| byte_len、header_len | 各 4 | 总长度、头部长度 |
| tick、generation | 各 8 | 固定世界版本 |
| plan_hash、audience_hash | 各 32 | 计划指纹、宿主定义的公开受众组或私有查看者摘要 |
| room_name | 8 | UTF-8 arena 的 offset/length |
| object_count、type_count | 各 4 | 对象数、类型桶数 |
| terrain、object_directory、type_buckets、variable_arena | 每项 8 | 各段 offset/length；不存在则长度为零 |
| reserved | 16 | 编码为零，版本 1 拒绝非零值 |

对象目录按 ID 升序，记录 `(id: u64, type_handle: u32, row: u32)`。类型桶含行数与字段目录；字段目录标识句柄、编码、缺失/null 位图及数值列或变长描述符位置。定长值按行定位，字符串/数组惰性解码。内建与扩展遵守同一目录，不能附加未授权 Generic 原文。

缺失、null、零和空数组分别编码，缺省与 JS 暴露由字段描述决定。u64 ID 保持精确，玩家仍用字符串，不经过 JS Number。浮点拒绝 NaN/Infinity，引用与集合使用有界结构编码。

解码前检查字节/对象/字段/集合限额、偏移加法溢出、非法重叠、UTF-8、重复 ID、未知句柄、type/row 关系、坐标及指纹。限额作为显式运行配置在原型中测量并记录，编码器同样受限，超限不得发布半块数据。公开/私有块只能在相同 tick/generation/plan 下合并，同名字段不能互相覆盖，冲突在冻结时拒绝。

`audience_hash` 只用于一致性校验和缓存分组，不是授权凭证；块句柄由宿主按真实玩家身份发放。房间名及所有变长描述符必须位于 arena 内；目录、位图、数值列须完整落在其所属段内。未知版本和 flags 明确拒绝，不能尝试按旧布局解释。

不可变引用计数句柄随 `RunEpoch` 派发，固定公开块与 overlay。新版本不能原位修改旧块；超时拒收回执不等于旧内存可复用。工作者实际结束或沙箱销毁、引用释放后才回收；失联的原生执行仍持有句柄时须保留，并报告固定代际与内存量。

Rust `Arc` 不使 V8 ArrayBuffer 自动只读。玩家不得取得共享块的 ArrayBuffer、TypedArray 或可写宿主句柄，包装器和可信解码层只返回授权值。必须验证 backing store 的可写访问和存活期，不能用隐藏变量名代替隔离。不能安全保证共享直读时，使用每 isolate 私有拷贝作为参考路径并记录复制成本，不发布可写共享内存。

性能目标是字段在沙箱本地解码，不逐属性发线程命令或往返宿主通道。可信解码层捕获必要内建函数，避免玩家改写原型取得缓冲区或干扰权限。保留参考路径时不能宣称完成共享直读验收。

## 7. 模块职责与提交边界

| 模块 | 职责 |
|---|---|
| `kk-mod-api` | 描述、键、冻结校验、计划与规则纯数据；无引擎/VM 依赖 |
| `kk-core` | 通用 ID/版本，保留未迁移默认常量 |
| `kk-schema` | 权威与玩家协议布局/编解码；不计算查看者权限或安装处理器 |
| `kk-world` | 权威/扩展状态、字段适配、按计划裁切 |
| `kk-engine` | native 绑定、意图、候选更新、处理链与发布校验 |
| `kk-runtime` | 装配计划、固定视图、派发和生命周期、授权通道拼装 |
| `kk-runner` | 视图消费、包装器/预检、意图记录；不写权威对象 |
| `kk-mod-host`（C） | JS 加载、回调和玩家模块；通过纯数据连接引擎 |

依赖向基础数据层流动，world 不能为读取规则反向依赖 engine；native 表留在 engine，不能把 `Working` 带入描述层。计划可跨线程共享，候选只在结算线程变更。

扩展状态沿用 prepare/settle/validate/publish。失败重试复用已确认玩家结果和同轮输入，不重跑玩家。B 只验收普通失败的内存回滚，JS namespace/VM 全局恢复、外部输出和磁盘原子性留给后续阶段，不因描述层建立而视为完成。
