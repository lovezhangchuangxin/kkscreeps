# 注释质量调研与整改方案

日期：2026-10-01。源码调查基准：`ffece3a6fbcb7c2bf188c4bfbac0a85388598570`。

本报告在误删后的复核中重建，保留原调查的方法、统计、主要证据、改写示例与整改建议，并补充规范和词典的核对结果。配套文件：[注释规范草案](../contributing/comment-style.md)、[术语词典](../glossary.md)。这些是方案文档，不代表自动检查已经实施。

## 1. 结论与范围

现有注释确实存在大量依赖开发背景的表达。长期维护需要的行为说明、上游依据与短期评审历史混在同一段；“门、面、壳、真化、清偿”等词省略了对象和条件。部分文件头与能力说明已经过期，可能误导维护决策。

需要分别处理三类问题：**事实错误、表达难读、依据尚未核实**。不能把全部难读注释判为失实，也不能只润色文字而保留错误结论。

“夹带私货”在本调查中只按可观察问题分析：注释夹入模型名称、评审过程，或者把局部意图写成未经限定的项目保证。没有证据判断作者动机。技术术语、兼容性例外和错误实现对照本身不应被禁止。

本轮进行全量近似文本扫描与重点源码核对，不是逐条语义审查全部注释，也未重新验证所有上游一致性说法或执行全量游戏测试。本次修订只改文档，不修改源代码、兼容性基线、hooks 或 CI。

## 2. 扫描方法与数量

使用 `git ls-files` 限定跟踪文件，扫描 `crates/`、`compat/src`、`compat/scripts`、`compat/test`、`scripts/`、`apps/`、`packages/` 和 `spikes/` 中的 `.rs/.js/.ts/.mjs/.sh/.cc/.h` 文件。排除 `assets/`、`native/`，因此不评价第三方 lodash 和 native 原始源码的风格；未跟踪 bot 夹具也不参与。

识别行首 `//`、从行首开始的 `/* ... */` 块，以及 shell 行首 `#`。块内空白行也计入，不计行尾注释。此方法不是语言词法解析，不能可靠处理所有字符串与内嵌语言。Rust 常量生成文件的头部包含在统计中，后续整改应修改生成器而非产物。

## 4. 应保留的好信息

- `kk-pathfinder/src/ffi.rs:3–21,189–192`：指针有效期、回调矩阵存活期、panic 边界、释放责任和地形并发限制。这些条件不能为缩短注释而删除。
- `kk-runtime/src/embed.rs:41–49`：重试不重跑玩家、复用首次墙钟输入、提交后清空缓存。去掉批次和“输入钉子”后仍是有用说明。
- `structures_spawn.js:65–70`：存在性判断并不等于完整类型检查，是重要的调用约束。
- `kk-runner/tests/sandbox_tests/resource_host_and_nearheap.rs:605–609`：为什么用 typeof 检查属性不存在，为什么 Object.isFrozen 在此没有区分能力。
- `compat/src/adapter.ts:46–47`：Symbol.for 标记让错误跨模块实例识别，不需要共享模块图。
- `scripts/gen-constants.mjs`：来源、运行方法、产物和类型映射，帮助维护生成器。

`watchdog.rs` 的同步与销毁顺序说明也有价值，但“否则一定丢失唤醒”等强结论仍需结合同步协议核实，不能因注释详细就默认正确。

## 5. 改写示例

以下是建议，尚未应用到源代码。

原文：

```rust
//! store 领域语义：正量键集共核（两投影的契约折叠各自定型）。
```

建议：

```rust
//! 构造资源存储的 JSON 字段，只加入数量大于 0 的资源。
//!
//! 查询快照和沙箱世界数据共用这段过滤逻辑。
//! 沙箱世界数据还会补充 energy 字段，即使其值为 0。
```

重试缓存建议：

```rust
/// 缓存世界结算失败时的玩家运行结果。
///
/// 重试不再次执行玩家代码，而是复用首次尝试的指令和 TickInput。
/// 这样控制器签名时间不会随重试改变。提交成功后清空缓存。
```

类型判断建议：

```js
/** 检查 id 是否仍存在于当前 tick 的结构数据中。
 *  source 和 mineral 也使用 raw type='structure'，本函数不能独立验证类型。
 *  调用方必须另外检查对象类型，或排除这两类对象。 */
```

测试接口建议：

```rust
/// 测试用故障注入：使下一次世界结算返回错误。
/// 此公开方法在生成文档中隐藏，但仍可由代码调用。
```

错误实现对照不必一律删除。例如 CPU 桶恢复注释可以解释“先比较原余额，再选择恢复方式”，并用明确数值说明 `(bucket + limit).max(-2 * limit)` 为什么不等价；无需保留是谁、哪轮评审发现。

## 6. 整改与验收建议

1. **先人工试改**：从模块头、重试缓存、类型判断和测试说明各选代表，确认规则不会删掉重要限制。
2. **先修事实矛盾**：能力说明、测试接口保证、数据层级、旧路径，改局部时同步文件头。
3. **按职责分批清理**：协调与结算 → 玩家 API → 世界数据与格式 → 测试 → 工程入口。发现实现错误另立修复，不夹带业务变化。
4. **后续建立来源记录**：保存上游仓库、版本与主要符号；不以裸行号或个人机器路径作为唯一依据。
5. **先提示再评估阻断**：自动工具须识别注释和完整块、限定跟踪文件、排除生成与第三方内容。关键词只辅助阅读，不能证明注释真假。

不以“黑话零命中”“每段不超过三行”“删掉一半注释”“所有函数都有注释”等机械指标验收。读者应能在没有开发历史的情况下回答行为、原因与边界；审查者应能在实现、测试或可靠来源中核实说法。

纯文档变更检查 diff 与链接；源码注释整改再检查代码格式。可执行 Rust 文档示例需要相关 doctest，安全、并发和事务断言需要核对保证范围。

历史调查和审计保留原始证据；规范可取代其中的写作建议，不应因此删除整份报告。已解决问题更新处置状态，不将依据一并删除。
