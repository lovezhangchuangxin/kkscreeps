# 性能关键路径再调研（2026-10-11）

属性：**源码调研与待验证方案**，不是现行架构或性能交付报告。基线 `525ec789`，入场工作区干净；本轮未构建、未跑新性能窗口、未改变运行实现。历史读数来自 [11 的 L1a 后补记](11-mature-performance-optimization.md)及其既有证据。当前接手统一见[台账](../plans/mod-next-batches.md)。

## 结论与差距

下一阶段应把重点从“全量工作做快一点/搬去别的线程”转向“消除全量工作，以及缩短真正的依赖链”。推荐先做稀疏投影和静态地图常驻，再做字段级失效与私有索引增量；房间结算流水线是潜在的大收益项，但必须先拆共享候选状态，不宜直接线程化。

已有证据：

| 时点 | wall | CPU | 限制 |
|---|---|---|---|
| row-dirty 后 | kk/xxs 1.559× | 0.775× | 既有热稳态短窗 |
| L1a 后静默 w5 | kk 401.2ms，xxs 约 287ms，1.3971× | 1660 core-ms/tick，比例 0.932× | 单个短窗，不能当正式达标依据 |
| L1a 后热浸 w6 | kk 494.1ms，比例 1.6331× | 见历史补记 | 机器状态显著影响比例 |

用 w5 只做量级预算：达到平价需再削约 114ms（28%）；达到既有讨论中的 0.9× 需再削约 143ms（36%）。project/run/settle 的 P50 约 66/185/143ms，是选调查方向的参考；**分位数不能逐项相加当作某一 tick 的实测分解**。把 project 完全消掉也不够达到 0.9×，必须同时处理 run 或 settle/二者重叠。

CPU 总量已经接近平价甚至更低，证明 Rust 路线并非没有效率收益；wall 仍落后说明工作分布、屏障和主线程路径重要。但 CPU/wall 不是瓶颈的充分诊断，不能把主线程等待一概叫作可利用空闲核。

## 源码核对到的结构成本

### 1. 对象是局部视野，传输框架仍按全服展开

[kkpv_bundle_for_viewer](../../crates/kk-world/src/kkpv/mod.rs) 为每个玩家遍历 `self.rooms`，不可见房也放 empty 块；`kkpv_envelope_for_viewer` 同样逐玩家构造全房目录，理由是 `Game.map` 需要区分注册房与界外房。

50 玩家×300 房意味着每拍 15,000 个私有房块及目录条目处理。若每人只见自己的六房，可见房关联仅 300；observer 等会增加关联，不能硬编码六房。这里的 50 倍是**目录处理数量比，不是整个投影的预期加速倍数**，可见对象编码与读取并不会因此减少 50 倍。

[public_bundle_for_epoch](../../crates/kk-runtime/src/embed/projection.rs) 按运行代际重发公开地形；[世界侧](../../crates/kk-world/src/kkpv/mod.rs) 每次构造全部地形块。物理 backing store 已共享，不能再宣称消除 50 份地形字节拷贝；剩余浪费是每拍重编码，以及 50 个 isolate 分别解析 300 个块、创建视图和地形表。[world-tick.js](../../crates/kk-runner/src/prelude/runtime/world-tick.js) 明确每拍调用 `decodePublicBundle` 并重建 `terrainByRoom`。

### 2. 常驻对象之后，索引与查询仍每拍全建

[world-tick.js](../../crates/kk-runner/src/prelude/runtime/world-tick.js) 全量建立 `rawById`；[game.js](../../crates/kk-runner/src/prelude/game/game.js) 全量建立 `objectsById`、房间桶、Game 名字集合并回填 `room`；[queries.js](../../crates/kk-runner/src/prelude/game/room/queries.js) 每房重新构造类型及空间索引。

共同成熟房每房仅道路/墙/rampart 就有 420 个，另有功能建筑和 14 个 creep。大量对象的值可能变化，但它们的 ID、类型、房间和位置不变。用“对象行有变化”触发所有索引维护粒度太粗。此前单次分桶减少了重复扫描，但仍然是每拍全量扫描。

### 3. 行级脏位没有解决脏行内的大字段复用

[kkpv.js](../../crates/kk-runner/src/prelude/game/kkpv.js) 的 `updateResident` 对一条脏行重新安装所有变长字段访问器。一个 creep 的位置、TTL 或疲劳改变，便会令未变化的 body/name 等字段重新物化。干净行已经跳过，这一收益不能再次计入新方案。

`records/his/los/ends` 数组和桶布局元数据仍每拍构造；可以测量，但先不要为了免分配而把可达对象永久缓存。尤其不能保留玩家改过的嵌套数组/对象再误当作权威数据。

### 4. 全局玩家屏障仍然存在

[run_players](../../crates/kk-runtime/src/embed/execution.rs) 等待 `execute_players` 收齐结果后才进入结算；[settle_rooms_stage](../../crates/kk-engine/src/settle/pipeline/engine_tick.rs) 逐房串行调用规则。

当前 L1a 是“本拍结算房间后，提前编码下一拍投影”，没有把本拍玩家执行与本拍规则结算重叠。这与之前被证伪的“投影预取/就绪玩家队列前瞻”也不同。

本地 xxscreeps 核查版本为 `5ff0d1a682170f6b5f9c8bac3e703767625988e0`，源码根目录 `/Users/keqing/Desktop/projects/sources/screeps/xxscreeps/packages/xxscreeps`：

- `engine/processor/model.ts::publishRunnerIntentsForRooms` 按房递减待到玩家数，归零通知 processor；
- `engine/service/processor.ts` 消费已就绪房，多 worker 处理并保留房亲和；`finalize` 等玩家及首阶段完成后运行；
- `schema/overlay.ts::injectGetters` 从 buffer/offset 生成读取器，对非整数读取做物化缓存。

因此值得借鉴的是**依赖就绪调度和接近玩家访问形态的数据表示**。不能把 xxscreeps 的速度概括为 TypeScript/V8 比 Rust 快，也不能忽略其不同阶段划分。

### 5. 结算有 JSON 成本，但尚未锁定最大调用者

[GenericData](../../crates/kk-schema/src/generic_data.rs) 已共享不可变文本并缓存身份；`identity()` 的首次读取仍解析完整 JSON，载荷每次替换都会建立新身份缓存。[decode_store](../../crates/kk-world/src/domain/generic.rs) 仍解析整条记录，多个建筑/经济动作亦有 `from_str`/`to_string`。

这能证明存在重复解析的候选路径，**不能据此把历史 serde 样本都归因于 Mod 校验或某一个函数**。先统计调用次数、输入字节和调用栈，随后挑主路径；不推荐为所有 Generic 永久缓存完整 `Value` 树，内存及缓存局部性可能得不偿失。

## 建议的实施片

### P1：稀疏私有束 + 独立静态地图版本

这是下一实现片的首选：已有 O(玩家×全服房间数) 源码证据，跨宿主与 V8 都能减工作，且不用先重做规则事务。

1. 把全服房目录、状态和地形放进按内容版本缓存的公共地图快照；tick 信封引用版本。房态有墙钟含义，缓存数据不等于冻结 `Game.map` 的时间判断。
2. 私有束只带可见房，以及不可见但仍需导出的自有旗/工地等对象所属房。保留原有授权谓词；移除空块不等于禁止不可见房 API。
3. 房间关联通过可见性/归属索引枚举，不能仅删输出空块却保留逐玩家全房扫描。
4. 解码归并从“第几个块”改成“房间稳定身份”；进入视野走 full、离开视野清扫，跳拍/基线不符回退。不要把块序错位的慢路径永久化。
5. 拆分“本次投递的 tick/generation/plan/audience”与“不可变内容版本”。不直接关闭原有 tick 校验；消费点验证当前信封授权了这个内容版本。换计划、编辑地形、恢复、换包、沙箱重建都要失效。

两片可分别验证：先做公共地形/地图常驻，再做稀疏私有房束。指标包括全服扫描数、空块数、地形解码次数、信封字节、project/run/端到端 wall 和 CPU。保持 JSON 参考路径及全量 KKPV 回退用于对照。

**实施序修正（2026-10-11 复审采纳）**：先落低扰动计数再动任何子片；公共地图版本化的 wall 收益可能有限——地形解码摊到并发 worker 后仅为数毫秒量级，P1 的大头在稀疏私有束砍掉 O(玩家×房间) 的目录/空块处理与 JS 索引装配。若计数显示前者收益低于分辨率，直接先做后者，不按文档顺序机械推进。

### P2：字段级失效，并把身份/位置变化独立出来

先挑会频繁改变但大字段相对稳定的记录验证，例如 creep。为字段保留比较结果或版本，使位置/TTL 变化不再重置未变 body/name；布局变化、missing/null 变化、嵌套值变化仍可靠失效。

优先利用编码端已有逐格 dirty 比较，避免在每个 isolate 再做一遍大字段深比较。首片可只处理变长字段位图，不急着把 wire format 变成跨拍 delta 协议。不要把 64 位非加密哈希相等当作正确性证明；精确字节比较或完备写入版本需要有可靠来源。

随后增加独立的 membership/position/type/owner 变化摘要，让私有 `rawById`、`objectsById`、房桶、look 空间索引跨拍维护。结构的 hits/store 变化不应重建空间索引；移动 creep 只改旧格与新格；出生/死亡/转房/变类型单独处理。

公开 `Game.creeps`、`find` 返回数组等仍可能被玩家修改，应按契约重新给出结果或保护内部缓存。第一片只常驻闭包私有索引，不把玩家可写数组直接作为内部权威缓存。旧引用、用户自挂字段、原型补丁、嵌套数据修改、Mod 包装、观察视野退出都需要回归。

### P3：发布时产生变化集，避免编码后再发现没有变化

当前 row-dirty 是“全量编码新字节，再逐格比较”；L1a 是“把同一份全量编码搬进结算窗口”。下一层结构收益来自在写入时记录变化，供编码、索引、验证统一消费。

建议从单房独立派生缓存开始：稳定字段布局 + 已编码行/列页 + 对象增删及字段变化集。先复用未变行的编码输入或字节，继续产出完整块；验证有效后再考虑传 delta。这样避免一开始同时承担权威存储迁移、wire 迁移、恢复迁移三种风险。

所有原生、Mod、跨房、市场、管理编辑、恢复写入都必须覆盖；拿不准的路径整房标脏，不能靠遗漏来获得高命中率。校验覆盖完备后才可用房内容版本替代 L1a 的候选深比较。派生缓存不进入权威检查点，冷恢复可重建；若新增权威表示则同片处理版本迁移。

同时考虑将一个房间的可共享内建对象与受权限约束的 Mod/扩展字段分开：目前一项扩展就使整房退出共享快路径。应按有效权限与计划分组共享，不能只按对象类型或“有 Mod/无 Mod”粗分，更不能把 owner 字段混入公共缓存。此项防止默认场景收益在实际 Mod 使用中消失，收益尚未测量。

### P4：房间依赖调度，保留统一提交

这是最可能明显缩短剩余关键路径、同时也是风险最高的方案。先做不改变执行顺序的 trace：玩家完成时间、房间所需输入全部到齐时间、每房规则时间、全局阶段时间、编码开始/结束。计算在真实完成序下有多少结算可提前，而不是用主线程等待时长代替潜在收益。

设计目标：全部玩家仍读同一个已提交 W(t)；输入到齐的房在候选里先结算；跨房/市场/账号与世界级处理按既定顺序收敛；全部成功后，W(t+1)、Memory、CPU 一次发布。失败保留玩家结果，只重试结算；提前结算结果不能提前对后续玩家可见。

依赖不能仅按房主或可见玩家推断：敌方单位、不可见房动作、全局指令、NPC 及 Mod 跨域能力都要纳入。无法证明局部性的动作留到全局屏障；未来开放的新能力不能静默走错旧快路径。

当前 [TickState](../../crates/kk-engine/src/settle/pipeline/txn.rs) 的 `Rc<RefCell<SharedState>>` 把 players/next_id/mod_states 绑在一起，规则又可能观察前房写入。所以实施步骤应是：

1. 分类共享操作：可交换增量、只读快照、必须有序的读改写；只有经验证可交换的操作才输出 delta。
2. 房局部事务输出 room 候选、事件、跨房请求及账户增量；全局修改有序汇总。跨房共享账户约束不能简单“求和再验证”替代原有先后语义。
3. ID 分配先保留稳定房序的串行创建路径。临时 ID 后补只适用于 ID 在合并前不可被规则/Mod 观察的情况；不要直接按房预留号码而破坏回放与引用。
4. 先验证房局部纯计算可并行，再与玩家执行重叠；共享 JS realm、Mod namespace state、顺序 RNG 均保持有序或走等价回退。不能拿 `parallelSafe` 声明代替实际读写域约束。
5. 不再无限增加线程：玩家、规则、预编码共享总计算预算；首先试主协调线程在等待回执时推进可执行候选，或让一个空闲 worker 接规则任务。是否能兑现取决于 CPU 竞争和实现边界。

理想化关系为 `project + max(run, room_settle, encode) + global_tail`，实际要算房级依赖、启动延迟与 CPU 饱和。L1a 已隐藏一部分编码；不能再把整个 settle、整个 encode 的收益相加。规则并行缩短 settle 窗还可能让下一拍编码 miss 变多，必须看跨拍稳态 wall。

### P5：以声明生成紧凑读写计划，减少 Generic 的反复 JSON 往返

作为中期方案，让冻结的类型/字段声明生成整数句柄、列/slot 访问计划与读写校验；Rust 热路径使用结构化数据，JS Mod 通过通用 SDK 访问，未知动态字段仍走通用侧表/JSON 回退。无需把每种新建筑写进 Rust enum，也不限定资源集合。

首个试验只选测量确认的 JSON 热调用：共享紧凑只读摘要，或房间事务内按需解码一次、更新后统一编码。先证明 CPU/内存净收益，再扩大范围。只有这样的渐进路径值得做；“全项目换 ECS/全量缓存 JSON 树”当前依据不足。

## 优先级、停止条件与验证

| 顺序 | 交付片 | 主要理由 | 继续条件 |
|---|---|---|---|
| 0 | 低扰动阶段/计数探针 | 历史粗采样曾误判 | 能区分全房框架、索引、字段重物化、纯规则与全局尾段 |
| 1 | P1 公共地图常驻、稀疏房束 | 明确的全服乘玩家复杂度 | 计数显著下降且端到端 CPU/wall 净改善 |
| 2 | P2 变长字段复用、私有索引增量 | 大量空间成员不变 | GC/分配下降，公开可写面与旧引用回归通过 |
| 3 | P3 变化集到编码缓存 | 从源头省编码与比较 | 写入覆盖完备、无未知失效路径 |
| 4 | P4 trace 后拆候选与调度 | 解决全局屏障 | trace 显示足够可重叠窗口，确定性/失败恢复证明成立 |
| 按归因插入 | P5 Generic 热路径 | 可能降低 settle CPU | 调用者归因成立，不增加难以承受的常驻内存 |

P4 的 trace 可以先于 P3 实施，但不应先大规模重写调度器。如果 P1/P2 降 run 后规则占比上升，再根据新 trace 重排，不机械按编号串行。

本轮不为这些方案承诺百分比。可设置明确的工程预算：例如分别检验是否能回收约 20ms project、50ms run、70ms 关键路径重叠；这些只是约 140ms 缺口的**验收预算示例，既非预测也不可简单相加**。小片低于分辨率且显著增加复杂度时撤回；仅凭微基准不交付整体加速结论。

测量继续使用现有唯一 50×6 夹具，不扩张近期验收范围：

- 测量分层（2026-10-11 用户拍板）：开发日常用分钟级短窗（compare-probe 5+100、进程内交替 A/B，块长可变避周期混叠）；批次收口用 ≥3 独立短窗取中枢 + 冻结 ABBA；500+3000 长窗只在最终验收出现（×2），不为验证等待数小时。
- 同一新鲜 release、冻结对照、双端预热、相同负载及执行身份；后台静默采样。跨进程比较交替先后，多窗报告中枢和散布，不能挑最快窗。
- 进程内开关对照也不是完全免疫热噪声：固定 25 tick 周期可能与 20 tick 寻路/市场事件等混叠。使用平衡顺序或不同块长，记录切换时缓存重建成本，并以独立冻结二进制窗口交叉验证。
- 保留总 wall P50/P95/P99、core-ms/tick、RSS、动作量和状态差异。优化索引、编码后，要核查真正工作量没少跑。
- 原始分相 trace 在诊断窗采，正式计时关闭高成本 profiler；不要从 sample 子树占比直接推出可回收毫秒。
- 少核部署中 `T >= CPU工作量/可用核数` 只是下界。在饱和且单位工作成本近似不变时 CPU 增长才近似反映为 wall 增长；历史“2 核会同幅反噬”是条件推论，不能替代 Linux 实测。

实现验证仍遵循完整门禁、重新构建 release、兼容棘轮和相关 Mod/恢复回归；本轮仅文档检查，不把历史通过数字记成新验证。

## 不建议继续作为主线的方向

- 继续提高玩家并发或固定加大 V8 半空间：已有本机场景负证据，后者还碰到小堆恢复边界。
- 再做一次房间 clone/BTreeMap 搬家并行：既有试验没有显示可观收益；它不代表真正规则并行已被否定。
