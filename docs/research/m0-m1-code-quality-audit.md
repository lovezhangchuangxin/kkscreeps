# M0/M1 代码质量复查

2026-09-28。范围是当前可运行链路：`kk-core`、`kk-schema`、`kk-world`、`kk-engine`、`kk-runner`、`kk-cli` 和 `compat`。前端包、存储和寻路仍是占位实现。本次以 [ADR-011](../decisions/ADR-011-engine-skeleton.md) 和[兼容性差异表](../designs/compatibility.md) 为行为边界，并对照本地官方 `system.js`、`create-creep.js`、`_born-creep.js` 检查关键规则。

## 代码路径

| 路径 | 职责 | 后续改动应守住的边界 |
|---|---|---|
| `kk-core` → `kk-schema` | 常量、地形与快照编码 | 数值与布局只在一处定义；解码输入要校验 |
| `kk-world` | 对象、房间索引、放置归一化、玩家世界投影 | 对象坐标和 ID 有效；投影保持 prelude 契约 |
| `kk-engine` | intent 清洗、单房结算、跨房统一提交 | 规则按既定阶段执行；失败不提交半个 tick |
| `kk-runner` | V8 沙箱、预算桶、看门狗、玩家 JS API | 沙箱销毁顺序与中断善后不可破坏 |
| `kk-cli` / `compat` | JSON-RPC 与 screeps-ok 验收 | 错误可归因；验收报告受通过率棘轮约束 |

## 本次发现与处理

1. `directions` 曾用相邻去重，`[1, 2, 1]` 会留下第二个 `1`。改为保序全局去重（对齐官方 `_.uniq`）；数字清洗按 JS `String()` 的十进制/指数形态分界（|v|<1e-6 或 ≥1e21 走指数形式取首位数字），与官方 `parseInt(String(v))` 口径一致。
2. 放置 creep、extension 等对象时，`store.energy` 从 `u64` 直接转成 `u32` 会回绕。统一使用饱和转换。
3. 快照解码曾静默覆盖重复对象 ID，并接受越界坐标；后续建立房间索引可能崩溃。现在拒绝这两类输入；指定 ID 的导入拒绝覆盖，普通插入会越过已导入的全局最大 ID。
4. `createShard` 曾重复解析地形，且字符串 RCL、重复房间或玩家名会被忽略或覆盖。现在先校验必需的玩家和房间数组及其中的名称，再回收旧分片；无效输入保留原状态。
5. 孵化与 creep 结算有若干只为占位而计算的值。已删除，并让出生落格复用统一的对象移动方法。移动仲裁不再克隆整张原始矩阵。
6. 部分注释记录了过期的 M0 状态，或与实现相矛盾（例如放置 creep 的 TTL）。已更新当前链路的模块说明和错误注释。

## 注释约定（2026-09-28 用户裁决版）

- 沿用仓库既有的证据链风格：模块头写职责 + 官方 file:line 对照 + 关键设计
  约束；"为什么不能简化"的机制知识（spike 阴性对照、V8 行为、官方怪癖）必须
  保留在离代码最近的位置。
- 在此基础上改进可读性：先说结论再说出处、一条注释一个要点、避免嵌套从句。
- 里程碑历史放 ADR/台账；已知兼容差异集中维护在 `docs/designs/compatibility.md`。
- 本文档初版提出的"模块头只写职责、行号一律外移"约定经用户裁决不采用（出处：M0 评审台账"代码质量优化轮"追记节）。

## 仍需关注

- M2 接入真实玩家 intent 后，应让清洗与执行器走同一条端到端测试路径；目前 embed 的玩家 intent 仍为空。
- `Generic` 对象可见但不参与多数结算。战斗、跨房移动、市场等规则仍按路线图后续阶段交付。
- 快照格式已能编码和解码，但世界级恢复、跨房 ID 校验与持久化入口尚未形成完整生产链路；接存储时需一起完成。

这些边界属于未实现阶段或已登记差异，不纳入本次局部修复。
