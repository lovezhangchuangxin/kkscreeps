# P1 玩家并发执行与线程 CPU 计费

本次基于 A4 提交 `c1a9a60`，实现 [P1](../../plans/archive/mod-plane-batches.md) 的有界玩家执行、命令期限与线程 CPU 计费。世界和房间结算仍串行，并等待本轮全部请求玩家结果；玩家执行与房间结算的流水线不在本次实现范围。

## 执行与回收

`EmbedEngine::run_players` 固定已提交世界的 time/generation 与玩家状态，按稳定玩家顺序准备 JSON 投影和 RunJob，最多保留配置数量的未完成任务。回收一个完成任务后补入下一个；所有结果进入按玩家身份排序的表，再按固定顺序合并意图。后续玩家投影期间，已派发玩家可同时执行，所有投影仍读取同一已提交版本。

默认并发槽为可用处理器数与 2 的较小值，不能随玩家人数增长。`set_player_concurrency(1..=32)` 可在轮次之间调整，失败轮存在时拒绝修改；1 可用于串行参考。该限制控制未完成玩家任务数，玩家线程与 V8 实例仍按注册玩家保留，不限制总线程数或实例内存。

每轮独立创建完成通知通道。通知用于唤醒协调器，实际结果来自每条命令自己的回执通道，并验证 tick/generation、执行尝试编号和工作者编号。旧轮通知不会积累到下一轮。`RunEpoch` 上移到 kk-core，runner 保留重导出；诊断 Tick 报告回带 JSON 的 time/generation，缺省为 0，不将缺省版本当作宿主权威版本。

RunJob 在派发时绑定绝对期限，默认是当前时刻加 tickLimit（至少 1 ms）再加 1 秒通信余量，也允许指定绝对期限。工作者开始前检查期限，过期的排队命令不注入内存、不执行玩家代码。期限覆盖内存初值注入、世界注入、求值和导出；看门狗取命令期限与原脚本墙钟期限的较早者，通信余量不延长脚本执行预算。回收采用带期限等待或非阻塞读取，回执还记录完成时刻，超过命令期限的完成结果拒收。

遇到基础设施故障后停止新派发，收回已派发任务直到完成或到期，保存已确认结果并保持故障门；不能自动重派。A4 的结算失败缓存重试、宿主桶权威和统一发布边界保持不变。命令期限不能杀死原生 Rust 区段永久卡死的线程，线程销毁仍需 join，因此不提供这种故障下重建或析构有界完成的保证。

## CPU 计量

macOS/Linux 通过 `clock_gettime(CLOCK_THREAD_CPUTIME_ID)` 读取执行线程累计 CPU 时间。正常计费与 `Game.cpu.getUsed()` 从世界注入前开始，包含入口、宿主 op 和写回在该线程上的计算，不包含排队、睡眠、其他线程工作及此前内存初值注入；指令附加费用保持不变。系统时钟错误明确返回，其他平台明确不支持，沙箱创建时检查时钟可用性。线程时钟含义参考 [Linux man-pages](https://man7.org/linux/man-pages/man2/clock_gettime.2.html)。

墙钟看门狗保留活性保护和 arm/disarm/terminate 代际锁规则。硬中断仍按完整预算生成费用，主动 halt 仍不计费且不回充，负桶轮保持原回充轨迹，正常费用仍向上取整。真实运行时间受调度、GC 等影响，因此不能要求不同运行的实际 CPU 账单逐位相同；串并行状态对照使用受控预算或桶封顶，纯预算回归检查费用与回充语义。

线程时钟回归在 macOS 本机工作区通过；同一份 `cpu_clock.rs` 在 Linux 6.12.54-linuxkit aarch64 容器、Rust 1.99.0、libc 0.2.183 中编译运行，通过 1 项测试。测试同时让另一线程忙算并让当前线程睡眠，检查其用量不被计入，再检查当前线程忙算确实增加 CPU 时间。Linux 验证范围是时钟模块，未运行完整 Linux V8 工作区。

## 复查修复

命令边界原先只解除看门狗，没有清除已经投递到 V8 的终止标志。在宿主调用已返回而看门狗刚投递的交错下，下一条 RunJob 的内存初值注入早于 begin_tick，可能被旧标志误中断。现在开始命令时先 disarm，清除终止标志并恢复堆上限，再 arm 新期限；结束命令也按相同顺序清理。确定性回归直接投递 V8 终止请求，检查新命令的内存注入以及命令结束后的管理操作均成功，修复前该回归失败。

性能脚本增加 P95 汇总后，报告入口仍只检查 P99，缺少 P95 的旧报告会在多次采集后以 KeyError 失败。现在在首份报告处检查各阶段的 P50/P95/P99；新增替身进程回归确认缺少 P95 时不采纳任何运行记录。修复前该回归失败。

上限选择使用首轮 P1 版本。先固定 32 玩家，使用相同 release 可执行文件，预热 100 tick、采集 500 tick，在每次重复中依次测试 1、2、4、8 个槽，各 5 次。完整样本见 [上限测量](p1-caps-2026-10-02.json)。

|---|---:|---:|---:|---:|
| 1 | 9.947 | 14.351 | 17.520 | 14.102 |

| 4 | 7.287 | 7.881 | 9.879 | 20.436 |

2 个槽在该负载下有最低 P50，CPU 消耗明显低于 4 个槽；4 个槽的尾延迟稍好。默认选择 2，避免仅按核数或玩家数扩大并发。该选择来自本机小房间负载，不代表所有机器和重型玩家代码的最优值。
