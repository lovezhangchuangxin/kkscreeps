# N2c 第二片：JS 治疗策略（2026-10-05）

基于 `c45610d`，开放近程/远程治疗槽中的 `ctx.combat.applyHeal`。作者通过独立 JS 指定同房目标和治疗量，宿主继续维护延迟队列、身体耐久上限、死亡与统一候选提交。现行契约见[JS 治疗策略](../../architecture/mod-heal-policy.md)，机器证据见[验收数据](n2c-heal-policy-2026-10-05.json)。

## 实现与复审

- SDK/op/引擎独立校验原始字符串 ID 和 0..=1e9 整数，拒绝小数、NaN、Infinity、越界及孵化/跨房/结构目标；读面允许作者主动正常拒绝尚未出生目标。
- native/JS 共用队列、动作日志和事件登记器；native 原部件/强化、距离、安全模式与目标预检保持生效。策略端不隐含这些功率和准入规则，但原玩家 wrapper 与意图清洗未替换。
- 登记时不截断到缺失生命；满血目标可抵消同轮后续伤害。共用对象 tick 在合并伤害/治疗后钳上限、恢复既有身体并判断死亡，无新身体/复活规则。
- runtime 的伤害和治疗共用 consumed 门与首触日志；对额外目标保存既有双队列，局部拒绝保留此前伤害/治疗、转账与后续移动。当前调用故障不能以 catch + decline 掩盖；跨调用旧 token 保持既有契约。
- 同轮伤害/治疗案例使用不同执行者，遵循 heal 压制同执行者 attack 的原互斥表；没有把被压制的意图误记为结算效果。
- 晚期 RawMemory 写回失败后重建原 realm、使用缓存玩家结果，治疗、Memory 与 Mod state 恰一次发布。
- flat-heal（固定 23）和 scaled-heal（缺失生命的一半向上取整）使用同一公共 SDK。分别选择后有不同计划身份，同时选择因多个 replace 明确冲突；没有包 ID 专用分支。
