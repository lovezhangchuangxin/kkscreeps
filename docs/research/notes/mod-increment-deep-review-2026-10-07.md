### R1：保护读取的整个检查点目录

`validate_paths` 对 `load_checkpoint` 只做文件路径相异检查；目录祖先保护只覆盖本次输出 `checkpoint_dir`。使用 `--load-checkpoint DIR --report DIR/ckpt-0000000002.json` 时，两者被认为不同路径。恢复读取成功后，`write_report` 覆盖输入文件。反例在复制的临时目录执行，原始备份保留；覆盖后文件顶层为 `report_version/success/status`，不再是检查点信封。

修复应在执行及失败报告写入前保护载入目录及其文件，并保留现有路径别名防护。补充成功、setup 失败、符号链接别名的反例；不要仅保护当前选中文件而遗漏可回退的其他备份。

### R2：游标必须绑定日志历史

两个独立运行 A/B 使用相同场景、种子与 Mod，各提交两轮。A 检查点玩家 Memory 为 `0.8081026448466624`，B 日志对应 Memory 为 `0.057428145387111273`。用 A 目录配 B 日志恢复，报告仍为 `passed`，`checkpoint_time=2`、`replayed_segments=0`、`log_cursor={last_seq:2,last_tick:1}`。零重放路径只核对日志头段 seed/引擎版本，不比较检查点与 B 的历史。

只核对 seq/tick 也不能区分两个独立历史。保存时须带可核验的日志链身份/游标摘要，恢复时核对该位置及连续后缀；有世界回退接缝的日志按经过验证的游标选区，不能始终从首个 `tick >= checkpoint_time` 的段选择。覆盖零重放、错误历史、接缝之后的新分支、日志截短与旧格式迁移策略。

### R3：继承已生效的切换历史

将现有 `sim-mod-switch/scenario-add.json` 的终态断言移除，保持玩法及模块不变，连续执行“运行两轮保存 → 恢复一轮保存 → 再恢复一轮”。前两次均 `passed`；第一份时间 2、切换 `[2]`，第二份时间 3、切换 `[]`；第三次 `setup_failed`，错误为“检查点 Mod 配置/选择/规则/预算/停用策略身份不匹配”。

当前 `switches` 是会话报告记录，不能作为完整持久切换历史。应继承已验证元数据并合并本次成功切换，拒绝的切换不入有效历史。补三次以上保存/恢复及切换拒绝路径；单次冷恢复等价测试覆盖不到此错误。

### R4：Date 的显式构造和实例方法并非全是纯函数

反例在 Mod 生命周期内保存 `Date.now()`、`new Date().getHours()`、`Date.parse('1970-01-01T00:00:00')`。两种时区的 `now` 均为 3000，后两项分别为 `0/0` 与 `8/-28800000`。文档已经排除 `Date()` 的本地文本，但这不能覆盖本地 getter、多参数构造、无时区字符串解析，也没有阻止这些值写入 state。

需选定并落实统一时区/日期 API 契约，明确不支持的环境相关面，而非只修文字。协议变化应同步版本策略、现行架构及跨进程回放/冷恢复验收。玩家 Date 保持既有输入源行为。

### R5：追加前校验不可变头段身份

反例准备只有合法 seed=42 头段的日志（创建后首轮前退出是合法形态），seed=43 世界续接并开启 `--verify-replay`。先成功提交一轮、日志由一行增为两行，之后状态才成为 `replay_failed`，错误指明“日志头段种子与引擎不符”。没有开启回放验证时，不兼容续接不会在该入口被拒绝。

`InputLog::open` 接收新头段参数，却在文件存在时完全忽略它。应在挂载时比较 seed、引擎版本等全日志不变量，避免先污染历史再报错；plan/执行策略/停用集允许按已有逐段协议变化，不能误变为全日志禁止切换。覆盖头段空日志、有数据日志与合法同种子续接。

### R6：检查完整图，保留合法链式压制

最小包声明 `a suppressedBy b`、`b suppressedBy c`、`c suppressedBy a`，三动作同对象、同接收者、同 scope；`mod inspect` 返回 `passed`。现行冻结仅查 `other.suppressed_by.contains(current)`，只能识别长度为 2 的环。应做完整图的环检测，并覆盖跨命名空间长环及合法 DAG。存在性判定“不看压制者自身是否执行”保持现有契约。

### R7：字段接口也要分配唯一符号

建筑 `playerClass: 'FooGauge'` 与 room-visible 对象 `playerClass: 'FooGaugeConstructorFields'` 均合法。`mod types` 输出两个同名 `FooGaugeConstructorFields` 接口；TypeScript 将它们合并。正常建筑字段赋值 `{'foo:heat': 1}` 报 TS2740，要求不相干的 `id/room/x/y/...`。

把字段接口加入 `Symbols` 分配，并使所有引用与说明读取分配结果。验收应编译真实消费者；仅 `--skipLibCheck` 检查声明文件不会发现接口合并造成的错误。

### R8：缺省字段与整集写面必须在样例中一致

使用文档中相同字段声明及 tick，补齐正常 manifest/player 绑定并手放对应 Generic 建筑，首轮 `run_failed`、提交 0 tick，错误为“缺少字段 label”。文档对 Missing 的读取说明正确，但整集写面要求写回全部字段；只用 `heat || 初值` 不能满足这个要求。

应决定 Missing 是否在写面保持可选，或让样例初始化 `label`/提供默认值，并说明完整约束。完整建造后首次 tick 和手放结构都应验证；这项首先是可复现的文档错误，不声称已决定新的字段语义。

### R9：障碍玩法与表示有效性须分开

G02 定义要求地形/结构限制可替换，且不允许 JS 放行后被隐藏 native 再否决。实际 `intent_move` 在 `has_static_obstacle` 后才登记，后置预检槽看不到这些请求；仲裁仍复检静态障碍。单向收紧可作为有效切片，但不能因此推导放行“语义惰性”并把父任务收口——这恰恰说明另一个消费者还没策略化。

坐标、ID、空间索引、最终占格一致性是应保留的宿主约束；穿越结构/地形的玩法规则应单独设计。建议把 G02 恢复为部分完成，登记静态障碍决策同源消费与必要玩家预检的后续切片；creep 让位链的动态依赖仍与 G03 分工。此项基于现有长期目标，不要求本次 review 直接开放全部放行能力。

## 架构与代码质量补充审查（2026-10-07）

用户随后要求进一步检查实现架构与代码质量。本节在同一 HEAD 上追加结论，不改写上轮证据；新增 **2 项 P2（R10、R11）**，与上轮合计 **5 项 P1、6 项 P2，均未修复**。以下架构建议与已复现缺陷分开记录，不能把建议本身当作已发生的运行故障。

### 可以保留的基础

- crate 依赖方向合理：`kk-engine` 不依赖 V8；`kk-mod-api` 持有声明与冻结模型；`kk-mod-host` 通过领域 Host traits 访问候选；`kk-runtime` 负责执行和生命周期。可信玩法 VM 与不可信玩家 VM 分开，适合继续扩展独立 JS 内容。
- 候选与发布边界清晰：`OwnedTickTxn/PreparedTick` 隔离已提交状态，世界/玩家/市场/state 随同一轮发布；`commit_tick_rooms` 在写入前检查覆盖、ID、坐标和时钟余量。冷恢复与包切换先装配替代分片，再切换现行分片。
- 已有质量治理有效：领域 Host traits、携带领域状态的 `ChainCapability`、共用 `intent_gate` 和内建能力分类降低了布尔门/状态错配；V8 生命周期账本被玩家与 Mod 共用；源码规模门禁和独立 JS/双通道/故障验证都有实际作用。`expect` 的重点位置由前置分类或局部控制流支撑，不能仅按数量把它们判为缺陷。

当前判断是“基础分层可继续，恢复与一致性机制需要稳定化”，没有证据要求替换整体技术栈或重新划分全部 crate。

### R10 / P2：建筑字段没有贯通公共编辑、恢复和发布校验

`validate_world_for_plan` 校验 Mod 对象与挂载扩展，`validate_stage` 同样只调用这两族校验，均未检查 Generic 记录中活动 Mod 建筑的自定义字段。`update_building_fields` 的 schema 校验不能覆盖管理放置、恢复或未改变字段的生命周期（桥接层对相同字段直接返回）。

最小独立包声明 `quality:gauge` 的 `heat` 为 `u32`、范围 0..100；tick 只增加 namespace visits。场景显式放置 `'quality:heat': 'not-a-number'`，玩家读取类型和值。首次运行一轮保存及冷恢复后一轮均退出 0、`passed`，玩家 Memory 两次都是 `{fieldType:'string', fieldValue:'not-a-number'}`。非法类型持续发布、持久化与投影，破坏字段声明契约。

主要位置：`crates/kk-engine/src/settle/checkpoint.rs:54–61`、`settle/validation.rs:60–61`、`kk-runtime/src/embed/mod_chain.rs` 的 unchanged-fields 短路。建议提取建筑记录的公共校验并接入公共编辑、恢复及轮发布，而不是在 CLI 单独拦截。手放结构允许缺键的现行规则与 Missing 策略应另行明确；本反例针对**已存在字段的非法值**，不要求把缺键全部改为错误。移除包后惰性 Generic 的既有语义也不能被无差别校验破坏。

### R11 / P2：逐个管理插入产生全世界复制与校验的平方级开销

`Engine::insert_object` 每次进入 `edit_world`，后者克隆整个 World；`validate_world_for_plan` 又克隆房间，并由 `adopt_edit` 做完整结构校验。`EmbedEngine::place_object` 和初始化控制器放置都逐次调用此入口。对不断增长的世界逐个插入 N 个对象，累计工作量接近 O(N²)。隔离副本的安全目的合理，但批量构造不应重复支付全世界事务成本。

外部临时 Rust 探针在新建单房间中分别逐个插入、以及一次 `edit_world` 内批量插入同样数量的 Energy 对象。三次串行 debug 运行的中位数如下；两路径均核对对象总数，单次提交与多次提交的 generation 本来不同，未声称完整检查点逐位等价。

主要位置：`crates/kk-engine/src/settle/state_api.rs:37–45`，消费者 `kk-runtime/src/embed/setup.rs:547–563`。这些数字仅为本机 debug 管理入口诊断，**不是 release 基准、每 tick 性能、RSS 结论或与其他引擎的比较**。建议优先让场景初始化/批量放置消费现有一次隔离编辑的能力；保持顺序、ID 返回、校验及失败原子性。若优化单对象编辑，再评估房间级副本或写日志，不能直接恢复裸可变状态暴露。

### 后续结构治理建议

1. **按职责缩小两个中心模块。** `mod_chain.rs` 941 行，`sim.rs` 935 行。前者同时处理调用转换、能力构造、state 暂存、trace、拒绝恢复和字段写面，`run` 本身约 300 行；后者把场景、包选择、恢复、日志与运行报告编排聚在一起。优先将桥接的调用初始化/提交恢复与字段适配分开，并把领域能力实现放进相应子模块。保留现有能力表，不再另建一份分类；拆分要减少修改传播，不能只挪行数。
2. **把恢复关系提升为运行时协议。** 当前目录选择、cursor 解码/选区在 CLI，核心身份与分片重装在 runtime，日志链在另一模块。R2/R3 表明跨模块关系没有统一验证点。建议 runtime 提供经过校验的恢复点/日志后缀，CLI 只提供路径、场景元数据和报告；切换状态的持久身份不应由“本次运行报告列表”临时拼装。
3. **将提交阶段写进错误类型。** `drop_log_for_io_failure` 在世界已提交后返回 `anyhow::Error`，与未提交结算失败共享 Result 通道，区别靠中文文案。当前代码和文档明确了这个边界，不作为新运行 bug；但接 backend/storage 前，应提供可机器判断的“未提交 / 执行结果未确认 / 已提交但日志输出失败”，避免调用方凭字符串决定重试。
4. **补宿主协议身份。** `execution_strategy_digest` 包含计划、停用集与派生槽链，但不含 Date/RNG/SDK 执行协议；runtime 检查点的宿主身份主要是 crate version。CLI 另有二进制摘要门，因此该入口已有更强保护。正式复用 runtime 的宿主应给影响玩法的宿主协议明确版本，并参与恢复/日志身份；黄金值和文档纪律不能代替运行时机器门。本轮未构建两版本宿主进行升级实验，不宣称已经复现跨版本错误恢复。
5. **以跨功能不变量补测试。** 现有领域测试和故障测试值得保留；主要不足是能力组合与重复生命周期：重复保存/恢复、错历史且零重放、跨时区、Generic 建筑字段与普通 Mod 字段的同契约、批量编辑失败等。用少量参数化状态序列补缺口，不机械增加镜像实现的断言。单文件与测试数量只作为门槛，不能代替这些关系验证。
6. **清理契约漂移。** `engine_tick.rs:147–149` 仍声称 publish 不返回 Result、World 不递增版本，而实际函数返回 Result，`commit_tick_rooms` 也推进时钟和 generation。上一轮门禁中的两个测试警告继续存在。它们不改变本次 11 项 P1/P2 计数，但会误导未来重构，应在稳定化批次一起处理。
