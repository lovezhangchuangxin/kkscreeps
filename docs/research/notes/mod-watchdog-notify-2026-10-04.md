# 看门狗通知合并：保持调用预算边界并减少重复唤醒

## 问题与实现

[逐 tick 诊断](mod-tick-diagnostics-2026-10-04.md)发现完整链每 tick 的进程切换计数明显多于 native/empty。源码中每对象调用 `VmBudget::start/finish` 都通知看门狗；短调用在已有 1 ms 定时监控期间反复唤醒线程，可能增加调度、锁竞争和 V8 安全点检查成本。本批据此做单一实现方向的对照，不把进程计数当作某一线程的精确归因。

`WatchdogState` 在原有互斥锁内登记工作线程的 Active/Idle/Until 等待状态。worker 每次等待前登记，在重新取得锁后转回 Active；arm 同步更新期限/代次，仅在 Idle 或新期限早于已有定时唤醒时通知。其他情况复用已有等待，工作线程醒来读取最新期限。disarm 同步清除期限并递增代次，原定等待可以自然结束；shutdown 始终通知并 join。

每对象预算 start/finish、线程 CPU/墙钟用量累计、返回时内存检查仍逐次执行。两次 Mod 调用之间的纯 Rust 工作仍不计入额度。玩法监控保持约 1 ms 周期，超限后持续中断到 disarm；普通玩家看门狗每代至多投递一次。状态与投递共用锁，解除武装返回后旧代次不再投递；已投递的 V8 标志仍由下一次执行清除。现行机制见[玩法预算](../../architecture/mod-execution.md)与[玩家沙箱](../../architecture/sandbox.md)。

## 验证与测试修正

新增真实线程测试覆盖：Idle 唤醒、更早期限打断 30 秒定时等待、取消期限后执行成功、长等待中的及时退出，以及资源模式到期后多次投递、disarm 后停止。已有玩家硬中断/复用和 300 次期限边缘竞态检查、Mod CPU/墙钟/内存及异常格式化矩阵继续通过。

新增宿主测试在同一结算轮中先成功调用，随后在 Rust 中实际消耗 30 ms 执行线程 CPU 并等待 50 ms，再成功调用；单轮限额 CPU 20 ms、墙钟 40 ms。它直接验证调用间工作没有被扩入 Mod 计费窗口。已有跨对象累计超限与失败重试/候选回滚检查继续执行。

两次测试失败保留在[验证记录](mod-watchdog-notify-validation-2026-10-04.json)：

- 新看门狗测试起初直接轮询 V8 终止标志，尚未进入安全点时观测不到请求。改为重复执行有界表达式，检查实际执行被中断；取消后的表达式必须成功。
- Release 的原累计预算测试假设每回调 4000 次平方根循环、400 个对象一定超过 15 ms；优化后整轮未超限而成功。将循环增加到 100000 次，另用诊断句柄断言实际经历多个 JS 调用，再检查资源故障和整轮回滚。没有降低限额或删除故障/世界/namespace/自动停用断言。

最终全仓检查通过：593 Rust 通过、10 个约定忽略，19 JavaScript 通过、0 跳过，格式与 Clippy 通过。相关四 crate 的 Release 测试 113 通过、5 个约定忽略；矩阵父测试实际运行超限子进程。重建 release CLI、核对 screeps-ok pin、显式构建适配器后，完整兼容性门禁为 1854 通过、153 失败、907 跳过，转红/转绿均 0。

## 测量与全部窗口

唯一生产源码差异在共用看门狗；上一批逐 tick 工具源码摘要保持一致。旧端是上一批二进制，SHA-256 `83d5fa2cb0c97901397e4f5949e795bb973eb27145c93529a908220882adce6d`；新端为 `89b73d73afde8564d112022f7d356e03ca10880588b4b21860dd8bda5e4039d7`。两者包括此前未提交的诊断工具；运行时 git 元数据不能作为编译来源证明，源码/二进制/日志摘要分列。

全部 30 个窗口保留，采集与构建/测试互不重叠：

- [逐 tick 探索诊断](mod-watchdog-notify-diagnostic-perf-2026-10-04.json)：两端各 native/empty/chain 一次，预热 100、采集 300；6 个诊断窗口、1800 条记录。按版本成组运行，仅作线索，不作为独立重复验收。
- [成对采集](mod-watchdog-notify-paired-perf-2026-10-04.json)：三个模式各三对普通窗口，另三对完整链阶段 profile；预热 100、采集 500。共 24 个窗口，逐轮交换版本先后并轮换模式；全部对象终态、精确链计数、包/预算和报告口径门通过。

复现配对配置：

```sh
python3 scripts/mod-perf-compare.py --before /tmp/kkscreeps-watchdog-before --profile --warmup 100 --ticks 500 --repetitions 3 --output /tmp/mod-watchdog-paired.json
```

### 诊断线索

单次逐 tick 完整链的进程切换计数由每 tick 439.813 降到 37.773，墙钟中位数由 26.946 降到 24.232 ms。计数属于进程全部线程，并且只有一次运行，不能精确定位某一线程或独立证明稳定降幅。

三对阶段 profile 的各端独立中位数（ms/tick）为：

| 阶段 | 旧端 | 新端 |
|---|---:|---:|
| budget_start | 0.096988 | 0.066606 |
| budget_finish | 0.555115 | 0.177336 |
| js_call | 25.011120 | 23.091540 |
| slot | 25.940528 | 23.637175 |

profile 的 CPU 成对中位降幅为 11.893%，仍与普通窗口分列。预算启动/结束直接计时合计约减少 0.408 ms/tick；JS 调用也下降，说明收益不能只由这两个计时阶段解释。减少监控唤醒带来的中断检查和竞争是可能原因，但未采每线程 CPU、监控回调次数或争用时间，不作精确成本分摊。阶段存在包含关系，不能把整槽、JS、op、host 耗时全部相加。

## 判定与后续

本地三对密集完整链均减少 CPU 与中位墙钟，探索诊断也减少进程切换；功能/资源/恢复/兼容门通过，因此保留通知合并实现。CPU 额度仍按每次实际调用结算，收益不是通过扩大预算窗口或取消资源检查取得。

这只是单房 400 link 的纯结算；没有玩家执行/投影、存储或网络，且未达到预热 500、采集 3000、五次独立运行的正式配置。桌面外部负载、温度与频率未控制，不宣称架构整体达标或所有模式零性能回归。后续先在稳定环境复核完整链与真实玩家闭环，并继续独立调查 native 与尾延迟；转换、候选写回等剩余成本须按现有直接计时再归因。
