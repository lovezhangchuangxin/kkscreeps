# Mod 执行故障来源（2026-10-04）

接续 [正常拒绝片](mod-intent-decline-2026-10-04.md)，各片均为 a8708d9 后的未提交工作区改动；保留前片原始证据，不追改其源码指纹。现行机制见 [Mod 处理链执行](../../architecture/mod-execution.md)。

## 选择与范围

此前槽调用故障只保留字符串，runtime 销毁 VM 后没有结构化执行来源。重复异常停用若据字符串猜测 Mod，会把内层故障误归给外层 wrap，也可能把全 realm 的预算超限误当成单个 Mod 的责任。

本片增加 ModFault（槽、可选绑定、阶段），沿最早的 SDK/候选故障边界留存。Rust read/write/转换记录对应绑定；native、非法绑定能力、共享预算与无法定位的整槽错误不指定 Mod。内层错误即使被 wrap 捕获并抛出新错误，也保留最早来源；普通异常消息格式化失败有备用文本。预算错误仍优先，且共享资源不强行逐 Mod 归责。成功路径不新增 JS/Rust op，仅增加本次能力的槽名保存；结构化错误在失败时构造。

runtime 的 last_mod_settlement_fault 返回 tick、房间、权威目标 ID 与宿主错误，记录存在 VM 生命周期容器中。销毁和重建不丢失记录；未进入引擎的拒绝保留记录；下一次实际结算清除记录，因此非 Mod 错误或正常拒绝不残留旧来源。该诊断不改变世界候选发布、玩家结果缓存与重试语义。

这是停用策略的诊断前置片，没有新增自动停用阈值、执行计划过滤或依赖处置，也没有逐 Mod 资源账本。绑定成员校验不是共享可信 Mod 的不可伪造身份；Mod 可以调用底层 op。尚未接入 CLI 协议、持久日志或直接 invoke 的绑定归因。

## 回归判据

- 两个 Mod 嵌套：内层 handler/read/write/转换失败，被外层捕获再抛错，来源仍为内层；诊断启闭一致。
- 异常消息伪造处理器名、消息 getter 抛错、Promise 不改变来源；重复 next 定位所属 wrap。
- native 和非法绑定能力故障不归给外层 wrap；正常槽与直接探针不伪造整槽故障。
- 真实 CPU/墙钟/内存及累计预算子进程矩阵：资源优先，只记槽、不记单一绑定。
- JSON/KKPV 均保留 tick/房间/对象/绑定，候选不发布；恢复失败、成功重建与结算前拒绝保留诊断；实际非 Mod 故障与后续成功结算清除旧来源。
