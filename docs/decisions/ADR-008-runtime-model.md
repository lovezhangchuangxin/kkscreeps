# ADR-008 运行时执行模型与资源管理

- **日期**：2026-09-27
- **状态**：已接受（用户对架构讨论中八项开放问题全部按建议拍板）

## 背景

核心架构（ADR-004）定型后，落地前还有八个执行层面的开放问题：线程模型、引擎同步/异步取舍、房间结算失败处理、tick 速率策略、沙箱抽象、世界生成排期、存储引擎选型时机、M0 的适配器形态。讨论后全部定案如下。

## 决策

### 1. 线程与实例管理：三层次模型

先澄清一个术语陷阱：官方**没有**"活跃玩家"的概念——官方每 tick 执行**所有**注册用户的代码（唯一例外是预算桶耗尽），因为没有世界存在感的玩家仍可写 Memory、生成 pixel、操作 InterShardMemory，跳过执行会被玩家观察到。我们严格保持这个语义，"活跃"只用于资源管理：

| 层次 | 语义 | 出处 |
|---|---|---|
| 要不要跑代码 | 官方队列语义：每 tick 全部用户（bucket 空的跳过） | 官方 `main.js` 用户队列 |
| 要不要处理房间 | 官方活跃房间语义：有玩家对象或本 tick 收到指令的房间才结算，其余休眠 | 官方 `activeRooms` |
| 要不要保留实例/线程 | **资源管理细节，玩家不可感知**：每玩家一个专属线程，玩家空闲时线程挂起（park）；V8 实例沿用官方的 3 分钟空闲销毁 | 官方 `user-vm.js:160-166` 同款 |

挂起线程的常驻开销只有几 KB 内存加一个调度表项，几百个挂起线程无压力——之前担心的"常驻线程过多"是伪问题；真正占内存的 V8 实例由空闲过期兜底（重建实测 <1ms、约 2MB）。

### 2. 引擎执行模型：同步主循环 + 数据并行 + 后台 IO

tick 主循环用**同步代码**驱动（tokio 单线程运行时承载，只为满足 deno_core 的事件循环要求）；房间结算用 **rayon 线程池做数据并行**；磁盘检查点写盘与网络推送放**后台线程**。不把引擎内部做成 async/await 风格——游戏 tick 是批处理不是高并发 IO，全异步会把确定性顺序搞复杂而收益很小。

### 3. 房间结算的事务性：失败即回退

结算出错时丢弃当前槽的半成品，房间保持上一 tick 状态，错误上报管理端，下一 tick 重试或冻结该房间。双缓冲结构天然支持这个回退，零额外成本。对照：官方出错只打一行日志、房间照常标记完成，可能留下半写状态——这是顺手的可靠性升级，不改变玩家可见行为。

### 4. tick 速率策略：默认跟随负载 + 硬上限保护

默认跟随负载（官方行为，忙时 tick 自然拉长）；但设保护上限——超过阈值时丢弃最慢玩家的执行（xxscreeps 的 abandon timeout 同款思路），宁可让个别玩家跳一 tick 也保住整体节拍。速率运行时可调（对应官方 CLI 的 setTickDuration）。

### 5. 保留薄的 Sandbox trait

不为换后端（deno_core 唯一，ADR-002），为测试：引擎单元测试需要一个返回固定指令的假沙箱，不想在单测里拖着真 V8 跑。一个真实现 + 一个测试假实现。

### 6. 世界生成：M1 预生成、M4 完整移植

M1 用"从配置加载预生成地形 + 手工摆放房间"起步；官方地形生成算法（`cli/map.js`，mod-10 扇区结构有细节坑）的完整移植放 M4，不阻塞主线。

### 7. 存储引擎选型：M2 基准后定

M1 不接真实存储引擎（内存 + 简单文件导出即可）；M2 对 redb 与 libmdbx 做基准对比后定，现在定是拍脑袋。

### 8. M0 的 screeps-ok 适配器 = 引擎嵌入式 API 的定义

适配器需要把引擎当库调用（跑指定 tick、注入代码、读世界状态）——这正是 `kkscreeps sim` 需要的同一接口。M0 的适配器工作与"引擎作为库"的 API 定义是同一件事，一石二鸟。
