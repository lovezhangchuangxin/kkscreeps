# ADR-004 核心架构定型：房间快照 + 流水线 + 索引 + 分层存储

- **日期**：2026-09-27
- **状态**：已接受

## 背景

第二轮架构调研把官方的开销归为四个来源，每一项都有实测或机制证据：

1. **整包复制**：每 tick 把每个玩家可见的全部世界数据（含整本市场订单簿，哪怕玩家不看市场）深拷贝进沙箱，估算每玩家每 tick 5~10 毫秒；
2. **全表扫描**：房间结算里的"按坐标找对象"操作逐个检查房间里全部对象，实测一个 50 爬爬虫房间每 tick 约 3.7 毫秒、约 8 万次逐个检查；
3. **全局等待**：必须等全部玩家代码跑完才处理任何房间；
4. **存储写放大**：私服把全部热数据放在单个文档里每 10 秒整体序列化重写（解包官方闭源组件实证），推算 40~110MB 每 10 秒；
5. **指令流的 JSON 文本传输**：玩家指令在进程间以 JSON 文本编码传递，二进制编码按第三方基准推算约有一个数量级的差距。

## 决策

五项对应的设计，在架构定型期落地（后改成本极高）：

1. **房间快照 + 共享内存直读 + 增量通道**：房间状态编码为连续二进制，沙箱按位置直读共享内存（约 2 纳秒一次），玩家没访问的数据零代价；市场等世界级数据只传变化部分。这同时决定沙箱与引擎之间的接口形态；
2. **50×50 格子索引 + 按类型分桶**：坐标查询从扫全表变查一格（实测约 80 倍提升）；
3. **按房间流水线推进**：某房间的玩家全部跑完立刻结算该房间，**预期** tick 时长受最慢的一个房间约束（推断；前提是玩家代码并发运行，即"一实例一线程"模型，待 M0 原型验证）；配固定房间顺序保证确定性（回放功能的前提）；
4. **分层存储**：热数据全部在内存，每约 2 分钟把变化的房间快照写盘（嵌入式单文件键值库），对照官方"每 10 秒整库重写"是数量级差异；跨机器扩展通过统一存储接口接 Redis 等，引擎不感知；
5. **指令在沙箱内收集、tick 末一次性传出**（二进制编码）：官方与 xxscreeps 两个实现都是这个形态，计费和幂等规则直接照搬。
