# ADR-004 房间快照、索引、流水线与分层存储

- **日期**：2026-09-27
- **状态**：已接受；投影协议与提交边界随后由 ADR-013/014 细化

## 背景

架构调研识别了五类候选成本：玩家世界投影复制、房间对象扫描、玩家与房间阶段的全局等待、存储写放大，以及指令编码与传输。

证据包括源码机制、局部实验和估算。单次查询、宿主读取或编码实验不能确定整体 tick 的收益，第三方编码基准也不能替代本项目端到端测量。采用版本、负载与原始结果见[架构深挖](../research/03-architecture-optimizations.md)。

## 决策

### 1. 房间快照、共享读取与增量通道

以版本化房间数据为基础，设计共享二进制投影与增量传输，减少按玩家重复构造、复制和解析数据。市场等世界级数据也应采用明确的版本与增量规则。

玩家只接收已授权的公共数据与私有视图，读取期间绑定同一已提交版本。按需包装可减少未访问字段的玩家堆分配，但编码、目录、授权和版本管理仍有成本，不能称为“未读零代价”。

[ADR-014](ADR-014-contribution-plane.md)要求整体设计共享字节、私有 overlay、惰性包装和扩展字段目录，再分步接入。生命周期、权限与布局验收见[快照契约](../architecture/snapshot-contract.md)。

### 2. 格子索引与类型分组

使用 50×50 格子索引缩小位置查询范围，按对象类型组织相关查询和处理。收益须包含索引构建、更新和内存成本；局部查询的倍率不能外推为完整结算提速。

### 3. 按房间流水线推进

玩家并发执行后，房间在全部潜在指令来源完成时可开始结算，与无关房间的工作重叠。潜在来源须包含跨房目标、不可见房间中的私有对象与扩展动作，不能只依据房间视野推导。

工作副本按确定规则合并，对象 ID、竞争结果和事件顺序不依赖任务完成顺序。无法证明依赖集合完整时等待全部玩家，具体要求见 [tick 契约](../architecture/tick-contract.md)。

“最慢房间决定 tick 时长”只是在资源充足、依赖可分离等条件下的理想化推断。跨房全局阶段、任务数量和机器核数都影响实际耗时。

### 4. 分层存储

热状态在内存中处理，已提交状态通过检查点写入嵌入式存储，优先保存变化数据。原方案以约两分钟的检查点周期作为设计起点，实际间隔须根据负载与可接受丢失窗口确定，当前没有运行中的默认周期。

跨机器后端通过明确接口扩展，但版本发布、确认、故障恢复和分布式原子性仍须单独设计。换成 Redis 不会自动保留单机提交保证，见[存储架构](../architecture/storage.md)。

### 5. 收集指令后统一导出

玩家 API 在沙箱内收集指令，执行结束后统一导出并由宿主清洗。保持动作覆盖、累计、计费和身份绑定规则；编码方式可以改变这些规则的表示，不能改变其结果。

二进制指令是目标方向。M2A 使用 JSON 信封接入，后续按投影与指令契约演进；原方案的二进制时间安排不代表已经完成。

## 实现与后续决策

当前已有类型化世界、格子索引、地形版本缓存和二进制房间编码。玩家世界与指令仍经 JSON 传递，完整共享视图、增量通道、并行房间流水线与游戏持久化尚未接入。

ADR-013 引入运行协调、显式时间输入和提交要求；ADR-014 进一步定义贡献计划、共享投影与全域候选。当前机制见[总体架构](../architecture/overall.md)和[游戏循环](../architecture/game-loop.md)，不能从“架构已接受”推导这些目标已经实装。
