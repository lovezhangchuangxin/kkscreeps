# ADR-002 玩家代码沙箱只采用 deno_core，不做备选后端

- **日期**：2026-09-27
- **状态**：已接受（用户拍板；取代沙箱选型报告中"deno_core 主力 + QuickJS 备选档"的原始建议）

## 背景

玩家上传的是不可信的 JavaScript 代码，服务器必须能：精确计量每个玩家用了多少 CPU 时间、超时强制掐断、限制内存、每个玩家一个独立持久实例、加载多模块代码。我们从官方源码提炼出十项硬要求，对 deno_core（V8 引擎）、QuickJS、Boa 三个候选做了真实工程的对比测试（每个候选都写了可运行的 Rust 实验工程，且由脚本复跑验证）。

## 决策

只采用 deno_core（Deno 团队维护的 V8 嵌入库）作为沙箱后端；不实现 QuickJS 备选档；Boa 出局。

## 理由

1. **能力全绿**：deno_core 是唯一十项硬要求基本全部满足的候选——超时掐断（在预算处精确生效、实例可复用）、内存硬上限（超限时优雅终止、进程存活）、启动快照（新实例创建提速 3~5 倍：两轮对照实验 4.4x/5.25x，游戏运行时整体入快照的实验为 3.2x）、原生函数注入（简单参数约 5 纳秒一次）、计算中途回调玩家函数（约 38 纳秒一次，官方寻路的 roomCallback 模式完整复刻）；
2. **引擎与官方相同**：玩家代码的语法兼容性和执行性能天然一致。QuickJS 慢约 12 倍——CPU 是预算制，同样的预算下玩家能做的事变少，这会改变玩家体感公平性，所以连"低内存备选档"也不做，避免维护两套行为差异；
3. **生产先例**：Supabase 的边缘函数服务用同样的方案跑大量不可信代码，安全加固的做法可以直接参考。

## 需要遵守的使用纪律（实验踩出来的坑）

- 实例必须按创建的逆序销毁（V8 的硬性约束，顺序错了进程直接崩溃）；
- 内存限制必须"设上限 + 注册接近上限回调"两道闸门一起用，只设上限会让 V8 崩溃整个进程；
- deno_core 自带的内部函数集合默认对玩家可见，启动时必须遮蔽；
- V8 实例不能跨线程挪动，采用"一个实例绑定一个线程"的模型；
- V8 引擎的安全补丁跟随 deno_core 发版节奏（不能单独升级 V8），运维上需要锁定版本 + 定期升级 + 安全事件应急流程（详见 [sandbox.md](../architecture/sandbox.md) 安全边界一节）。
