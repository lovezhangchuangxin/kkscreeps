# ADR-014 Mod 贡献定义、共享投影与全域提交

- **日期**：2026-10-01
- **状态**：已接受
- **前置**：[ADR-004](ADR-004-core-architecture.md)、[ADR-007](ADR-007-mod-system.md)、[ADR-008](ADR-008-runtime-model.md)

## 背景

Mod 作者只写 JS 后，默认玩法、扩展玩法、玩家投影与状态提交需要共用明确契约。调研发现，封闭对象与动作分派限制新增玩法，玩家投影重复构造和串行派发是候选优化点，市场也需要进入失败时可丢弃的候选状态。

这些结论来自记录版本的源码分析与局部实验。房间数、玩家数和代码负载影响耗时构成，不能把某次实验的占比当作全部世界的瓶颈比例。市场在后续实现中已纳入候选，早期“直接改已提交市场”的描述不再是现状。

本决策确立架构与实施约束，不表示完整 Mod 通路、共享二进制或全域事务已经完成。

## 1. 六项架构原则

### 1.1 启动时合并与冻结贡献

对象类型、字段、指令、规则覆盖、处理函数、玩家 API 和客户端贡献在启动时合并、校验并按依赖排序，形成不可变 ContributionPlan。运行时按冻结后的数组索引或完美哈希访问，不动态注册玩法定义。

冻结减少运行期注册与校验成本，但启动成本、计划大小和热路径分派仍须测量，不能从“已冻结”推导整体性能目标已经达成。

### 1.2 默认玩法使用同一贡献契约

Rust 默认行为注册到可包裹或替换的具名规则入口，数值规则通过 EffectiveRules 数据表提供。vanilla 不能绕过贡献契约形成扩展不可达的特权路径。

覆盖面按业务行为逐项验收：仅有事件观察或新增对象容器，不等于已有默认规则替换、指令执行和客户端扩展能力。

### 1.3 区分默认调用与扩展链

每个规则入口在冻结时选择 Native 或 Chained。没有扩展时调用默认实现；有扩展时执行 before、wrap、replace、after 等处理链，避免默认玩法每次重新判断注册状态。

原决策以一次 enum match 加间接调用作为默认入口额外分派成本的上限，保留这一实现约束。“无 Mod 零开销”是验收目标，不能与这项非零成本混为实测结论；默认基线须另做功能相同的对照，检查耗时和内存回归。

### 1.4 分离权威状态、玩家投影与贡献定义

| 部分 | 职责与约束 |
|---|---|
| 权威状态 | 类型化内建对象、扩展载荷及全域 TickTxn 候选，负责真实结算 |
| 玩家投影 | 公共数据编码一次并共享只读字节，按玩家叠加私有 overlay，VM 内按需包装字段 |
| 贡献定义 | 不依赖 V8 的数据契约，支持独立测试、校验与类型生成 |

共享二进制、私有视图、惰性包装和扩展字段目录属于同一投影协议，整体设计、分步实现。授权必须在交付载荷前完成；public、owner、server-only 等权限不能仅靠玩家 getter 隐藏。

按需包装可以减少未访问字段的 JS 堆分配，编码、目录、授权、版本保留和包装对象仍有成本。具体布局和收益按[快照契约](../architecture/snapshot-contract.md)与[性能验收](../architecture/performance-acceptance.md)验证。

### 1.5 全域候选一次发布

房间、玩家 Memory/segments/CPU 账本、市场、全局 ID、Mod 状态与提交后输出队列（outbox）都进入同一 TickTxn。全部可失败阶段成功后发布，外部副作用由提交后的明确协议处理。

Mod 的权威状态保存在 Rust 事务中，JS 堆只保存可重建缓存。候选回退、跨线程确认、磁盘持久性和输出幂等分别验收，不能用“统一 publish”名称代替这些保证。

### 1.6 分别发布默认兼容与 Mod 能力

无 Mod 的默认配置满足 [ADR-003](ADR-003-player-compatibility.md)。启用 Mod 的世界在握手中发布能力和内容指纹，允许服主明确选择改变规则；默认兼容与 Mod 能力分别提供验收证据。

## 2. 四项已确认选择

| 问题 | 决定 |
|---|---|
| 默认玩法是否使用贡献契约 | 是；从开放领域定义阶段起，新玩法同步声明具名入口和规则表 |
| 投影协议怎样演进 | 整体设计、分步接入；禁止先重复优化 JSON 接口，随后再另建一套不相干的玩家协议 |
| 首版玩法 Mod 如何隔离 | 管理员安装的可信 Mod 共用一个玩法 VM，后台 I/O 使用独立执行域；Mod 之间没有安全边界，玩家隔离不能降级 |
| 三方基准何时建设 | 本项目、调研版本 xxscreeps 与官方私服的同负载基准工具和 A 阶段并行；获得对照表前不得声称性能超过两者 |

需要逐 Mod 的资源归因或更强隔离时，再拆分 VM 或进程；共同可信意味着一个 Mod 可以影响其他 Mod，安装信任不能替代玩家隔离。

## 3. 开发约束

新增封闭 enum 分派、硬编码类型或行为白名单、内联规则常量时，必须同时提供具名规则入口或 EffectiveRules 数据通道；暂时无法开放时，在提交说明中登记例外、原因及后续处理阶段。

该要求在本决策接受后生效，避免新增默认行为超出 Mod 可替换范围。它与行为回归检查共同约束开发，不以获得性能收益为由绕过。

## 4. 实施方向与调整

接受[贡献平面方案](../plans/mod-plane-batches.md)的 A–G 方向，具体切片按阶段验收。保留四项调整：

1. 市场候选在 A 阶段早期完成；完成前不能在直接修改市场后增加可失败处理。当前市场已使用副本并随世界候选发布，完整事务仍有下述边界。
2. RunJob 合并注入与执行、有界并发和线程 CPU 计费与 A 阶段并行。工作者 epoch 是故障状态机前提；计费切换不得晚于 M3 多用户承载。
3. B 阶段的开放领域定义与整体投影协议设计合并，实际接入仍分步。
4. 不受这些边界影响的 vanilla API 扩展可继续，仍遵守第 3 节的开发约束。

三方对照工具与 A 阶段并行是已确认要求。若某个对照环境暂不可用，须记录缺失与影响，不能用局部 perf-probe 数据替代完整对照。

## 5. 模块边界

- kk-engine 不依赖 deno_core；当前已经成立，后续维持。
- 目标 kk-mod-api 保存纯数据描述与冻结计划，不依赖 V8 或 deno_core。
- 目标 kk-mod-host 提供 JS 装载、宿主调用、回调与后台调度，保持引擎与 JS 运行时的依赖隔离。

可以先建立边界再拆包；目标 crate 名称不能作为已有模块的证明。依赖方向和职责见[JS Mod 设计](../designs/mod-system.md)。

## 6. 取舍与当前边界

冻结定义与默认调用路径有助于减少动态查找；共享投影有助于减少重复复制；权威状态与提交契约使扩展参与同一结算。但实现成本包括接口覆盖、扩展链、权限过滤、旧版本保留、故障恢复与基准建设，性能和内存目标都须实测。

当前市场候选、结算阶段、恢复状态、玩家 Memory/CPU 候选及有界并发派发已有实现。ContributionPlan、KKPV 双通道与可信玩法 VM 已按切片接入；Mod 执行当前覆盖 link/对象意图，完整默认槽目录、投影优化、外部输出队列与磁盘崩溃恢复仍未完成。具体执行方式见 [ADR-015](ADR-015-mod-chain-execution.md)。当前执行与恢复范围见 [tick 契约](../architecture/tick-contract.md)，B 阶段的具体契约与实施顺序见[开放领域定义与玩家投影](../designs/domain-projection.md)。

本决策细化 ADR-004 的共享读取、ADR-007 的 JS 扩展与 ADR-008 的执行模型。ADR-011/012 的 JSON 过渡约束演进为整体投影协议；ADR-013 的接口先行和冻结前验证要求保留。默认兼容约束不因此降低。
