# 独立 JS Mod 完整玩法开发计划

## 目标与适用关系

根据用户 2026-10-05 确认的目标，独立 JS 包应能创造完整玩法，覆盖调研版本 xxscreeps 的扩展领域，并提供更完善的组合、恢复和开发工具。现状与源码依据见[现状复查](../research/09-mod-capability-current-audit.md)；原则沿用 [ADR-007](../decisions/ADR-007-mod-system.md)、[ADR-014](../decisions/ADR-014-contribution-plane.md)和 [JS Mod 设计](../designs/mod-system.md)。

本计划调整未完成工作的优先级，不替代[贡献平面批次](mod-plane-batches.md)已经记录的实现和证据。N 编号用于本轮完整玩法工作；不把既有 D4/D6 改名或重新判定为未完成。除下文标记已交付的切片外，其余为目标；当前机制以 architecture/ 为准，现状报告保留调研时结论。

具体后续切片、当前接手位置和每批更新要求见[Mod 后续任务台账](mod-next-batches.md)。该文件持续更新 G01–G30 的实际状态和证据，本计划维护总体目标与阶段范围；两者交付状态变化时同步，不在聊天中单独维护另一份进度。

2026-10-06 路线复审明确：G 父编号不是严格执行顺序，按台账的执行队列及子片依赖推进。作者 CLI/类型、覆盖清单和同功能性能参考前置；新增状态域当批扩展检查点/版本，不等完整迁移系统；异步后台宿主先于 JS storage，持久 outbox 再依赖输入日志与原子耐久发布，避免循环。网络和客户端的真实基础实现列入对应子片，不能当作已经存在的前提。

验收以业务闭环为单位：作者只改 JS 包及其配置、声明、资产，安装包后运行，不要求改 Rust 或重编服务器。宿主第一次实现通用能力需要 Rust 开发，但后续第二种玩法不能再靠新增专用 Rust 分支。

[ADR-016](../decisions/ADR-016-official-content-packs.md)要求项目自身以公共 SDK 开发官方 JS 内容，逐步提供可选内容包与玩法预设。交付要求见[内容包设计](../designs/content-packs.md)。首片的生命周期示例作为官方内容候选，后续扩成真实生产建筑；示例和正式发行内容的成熟度分别记录。

## 建议实施顺序

| 批次 | 交付与范围 | 完成条件 |
|---|---|---|
| N1 自主对象与作者入口 | 自有对象生命周期；同房候选对象读写/创建/删除；JS handler 依赖与有效规则读取；sim 装载 Mod | 一个 JS 包无玩家指令也能周期更新、自主创建及到期删除对象；有玩家 API 和场景断言；依赖/冲突可诊断 |
| N2 新资源与对象能力 | 开放资源目录、库存能力、建造配方与对象 trait；逐片开放伤害公式/移动仲裁等策略 | 新资源生产建筑可以建造、生产、搬运、受击维修、影响寻路；至少一种深层算法由 JS 替换且没有隐藏默认规则否决 |
| N3 房间/玩家/世界规则 | 对应域的意图与生命周期；服务端发射；地图初始化/NPC/周期输入；跨房和账户命令 | JS 世界事件跨两房生效并更新玩家状态；声明访问范围且实际检查；全局阶段与异常提交边界清晰 |
| N4 耐久恢复与升级 | 全状态检查点、manifest、包/schema/规则与执行策略身份；迁移、缺包恢复、输入日志与 outbox | 冷恢复连续运行与未中断参考一致；崩溃只恢复完整版本；迁移失败保旧版；缺包默认拒绝可写启动并可显式只读导出 |
| N5 服务与客户端贡献 | 后台 JS 服务、provider、路由/订阅/管理；资源资产、渲染与面板；玩家类型生成 | 同一 Mod 包贡献玩法、玩家 API、服务和客户端；至少一个业务 provider 与一个 JS storage provider 可替换；两类客户端分别验证 |
| N6 完整作者工作流 | init/test/watch、组合图/trace、故障夹具、回放与 tick 边界更新 | 作者用公开 CLI 重现冲突/拒绝/异常、定位绑定、保存恢复；更新失败保旧计划；报告绑定输入与执行身份 |

这不是全部串行的大瀑布：N1 的 sim 装载/诊断和 N4 的状态清单先行；N1 自主增删收口后先做当前域的基础保存恢复，不必等待 N3。N2/N3 增加域时同时扩展检查点与迁移要求。**N4 前置片基础检查点（2026-10-05 已交付）**保存当前完整已提交数据域、包/配置/计划身份、停用掩码与玩家工作者，接通显式 save/load 和 sim 冷恢复续跑；不包含周期调度、迁移或输入日志，现行机制见[检查点](../architecture/checkpoints.md)，证据见[交付记录](../research/notes/basic-checkpoints-2026-10-05.md)。N5 的契约在首次存储/网络设计时落实。N6 的测试和诊断随每片交付，持久回放依赖 N4。

默认玩法兼容与真实 bot 的 M2B 工作继续推进；不能为开放 Mod 放松零 Mod 棘轮，也不能以默认玩法达到通过率门槛替代 Mod 的独立验收。

| constants | 可扩展资源/类型/数值规则目录，玩家与服务端一致消费 | N1d/N2 |

| driver | 玩家运行连接器、输入/输出/持久数据的宿主集成；维持玩家隔离 | N3/N4/N5 |

## 已交付：N1a 自有对象 tick

2026-10-05 已接通自有类型的 `object.tick`、显式 sim 包加载和官方生命周期原型。公共入口为 `api.objects.define(typeKey, { tick(ctx) { ... } })`；不含 preTick、房间/世界阶段或通用增删。现行接口与顺序见[自有对象 tick](../architecture/mod-object-tick.md)，验证见[交付记录](../research/notes/n1a-object-tick-2026-10-05.md)。以下保留本片验收要求。

验收要求：

1. JS 声明对象生命周期处理器，经 descriptor、注册转换、冻结与装配门到真实对象 tick 派发；不以伪造玩家意图触发。
2. 每个已存在且仍存活的该类型对象每轮执行一次，稳定顺序明确；原生规则和对象动作后的候选字段可读；`ctx.state` 和自有字段候选沿现有校验/提交通路写入。
3. 明确生命周期是否允许 decline。首片建议只提供成功/故障，decline 在注册或执行时显式拒绝，避免借用对象动作的恢复边界却漏掉生命周期写面。
4. 保持 engine 不依赖 V8、mod-api 纯数据、JS 同步处理。进入 JS 前释放候选借用；next 和失败不可吞掉；当前可信共享 VM 和预算机制复用。
5. 给 sim 场景增加显式 Mod 包/配置加载，绑定内容与计划指纹；路径、未知字段和加载失败行为明确。不默认开启开发随机/时钟替换，不把固定场景宣称为任意脚本确定性回放。
6. 用独立 JS fixture 验证：零玩家意图连续更新、多个对象/两个房间稳定派发、玩家方法读取结果、JSON/KKPV 一致、处理器异常/超时后世界与 state 不发布、玩家缓存重试不重复执行玩家脚本、当前未加载任何 JS 包的原生默认参考路径不进入 JS。

完成这片只是接通自主生命周期，不能声称完整 Mod 玩法已交付。随后 N1b 接同房对象操作，才验证自主生成/删除的闭环。

## N1b–N1e：对象操作、组合、规则与内容选择

- **N1b 对象操作（2026-10-05 已交付）**：同房 Mod 候选 get/list、按 descriptor 创建/更新/删除当前绑定 namespace 的类型；维护 ID、位置索引及同格顺序、字段、查询和拒绝日志。不公开任意 RoomObject 整值替换或原生对象读写。动作出生本轮 tick、tick 出生下轮 tick、已删跳过，自删后 fields=null。nursery 公共 JS 原型完成自主生成/更新/到期删除，双房双玩家 JSON/KKPV 场景及故障恢复通过；现行接口见[对象能力](../architecture/mod-objects.md)，证据见[交付记录](../research/notes/n1b-mod-objects-2026-10-05.md)。原生对象读写及跨房能力继续随 N2/N3 开放。
- **N1c 组合（2026-10-05 已交付）**：JS dependsOn 转换为 handler depends_on，验证形状、缺失/循环、跨包及同槽/同 kind 约束；处理器返回稳定键。mod inspect、注册/运行时诊断及 sim composition 展示冻结和活动链、原始/替换中心、规则来源与停用闭包。多 replace 继续冲突，直接宿主拒绝不完整停用掩码。双房场景将实际 trace 与诊断核对，缓存故障重试与传递停用通过；接口见[组合架构](../architecture/mod-composition.md)，证据见[交付记录](../research/notes/n1c-mod-composition-2026-10-05.md)。尚无逐 tick trace、运行服务器停用 CLI 或持久输入事件。
- **N1d 有效规则读取（2026-10-05 已交付）**：玩法 JS 经 `api.rules.effective(key)` 读取冻结后的有效规则值（默认、单方覆盖、显式选择的多方覆盖），值由宿主从 `ContributionPlan` 与执行链同批装入 realm，随 PlanHash 一致；注册期读取抛错，处理器不能借注册闭包拿过期默认值，未知键为处理器故障。整数按双精度转换，配置/规则覆盖/玩家常量的区别、故障重试、重建与停用后继续返回原冻结选择均已界定并验证；现行契约见[有效规则读取](../architecture/mod-rules.md)，证据见[交付记录](../research/notes/n1d-mod-rules-2026-10-05.md)。运行期规则修改、规则迁移与检查点未实现。
- **N1e 新内容选择（2026-10-05 已交付）**：新世界启动期的显式包选择（`include`/`exclude`）经宿主 `RegisterOptions.selection`、sim 场景 `mods.selection` 与 `mod inspect --select/--exclude` 三处共用同一展开语义：manifest 依赖闭包展开并在报告列明自动加入项；未知包 ID、缺失依赖、显式排除与必需依赖相撞都带依赖路径整体拒绝；builtin 不可选（固定内建，随 N2/N3 迁移）。未选包不安装类型/规则/handler/玩家面与行为，configs/disabled 指向未选包报错，未选坏包不再阻塞；PlanHash 反映实际内容，组合报告新增 selection 并提升 report_version 2，恢复沿分片私有选择快照重建并核对原身份。manifest 依赖（参与展开）与 handler 引用（不参与、沿用未知处理器依赖错误）的边界已界定。内容预设语法未冻结，登记为后续。现行契约见[内容选择](../architecture/mod-content-selection.md)，证据见[交付记录](../research/notes/n1e-mod-selection-2026-10-05.md)。

自有动作扩大到对象增删后，必须扩大局部拒绝日志；生命周期异常则撤销整轮候选。ID 分配、对象增删及 namespace state 均须覆盖正常拒绝、整轮异常、晚期玩家写回失败与缓存重试。native 增删日志可复用，但先核对其现有作用域，不以“已有日志”代替完整覆盖证明。

## N2 的拆分和创作边界

先做资源目录，再做建筑能力，最后按示例需要开放深层策略，每片均贯通玩家预检、清洗、结算和投影。

| 切片 | 必须接通的消费者 |
|---|---|
| N2a 新资源（2026-10-05 已交付；建造/生产消耗已随 N2b 接通） | 命名空间目录、常量/API、库存表示与容量、搬运与掉落、快照；市场/跨房在开放前明确拒绝并登记后续入口 |
| N2b 建筑 trait/配方（2026-10-05 已交付） | 工地与完成对象、成本、受击/维修、障碍/道路/寻路、库存与生产、玩家查询与类型；客户端未实现期间用投影断言验收，不能把此阶段算作图形交付 |
| N2c 行为策略（单体伤害/治疗/群体伤害/反击表、原生 TOUGH 与 JS 受击策略已交付，其余未完成） | 原生伤害计算/应用或移动仲裁的具名入口；JS 可提供不同策略，宿主保留表示与事务不变量；另一领域继续登记为未完成 |

**N2c 首片单体伤害（2026-10-05 已交付）**：近战/单体远程攻击链中的 `ctx.combat.applyDamage` 和同房战斗读面，允许 JS 计算部件/生命值/护甲公式而不再调用原生功率计算。生命值、死亡/废墟、拒绝日志和统一发布继续由宿主维护；两个独立 JS 规则包及原生对照验证双通道和冷恢复。玩家预检的策略替换、移动仲裁与自有对象伤害 trait 尚未开放，不能据此宣布整个 N2c 或默认规则全量完成。现行接口见[JS 伤害策略](../architecture/mod-damage-policy.md)。

**N2c 第二片治疗（2026-10-05 已交付）**：近程/远程治疗链中的 `ctx.combat.applyHeal` 允许 JS 指定目标和治疗量，复用 native 延迟治疗、身体恢复与死亡判断；独立固定/比例治疗包、无 Mod 对照、局部拒绝、缓存重试和治疗前后冷恢复均有验收。默认玩家预检与动作互斥仍生效，其策略替换和上列剩余范围继续登记未完成。现行接口见[JS 治疗策略](../architecture/mod-heal-policy.md)。

**N2c 第三片群体伤害（2026-10-06 已交付）**：`ctx.combat.list` 同房战斗分页和 rangedMassAttack 中的 `applyDamageBatch`，由 JS 筛选目标与计算公式，先完整预检再应用，批量共用一次动作消耗。多目标拒绝保存此前队列，结构/孵化对象/索引/ID 可恢复；独立固定/距离衰减包、原生对照、双通道与进程冷恢复有验收。批量上限固定 256，玩家预检与移动等剩余面仍未完成。接口见[JS 群体伤害](../architecture/mod-mass-policy.md)。

**N2c 第四片反击表（2026-10-06 已交付）**：三个攻击槽的 `setRetaliation` 在执行前声明一次，按实际受击对象匹配反击量，可禁用原生反击或与 native/request/JS 单体及群体伤害组合。反击不递归、沿已有事件/延迟队列/死亡与拒绝恢复；双 JS 包、原生对照、反击致死重试及双通道冷恢复有验收。尚无实际主伤害量驱动的逐命中 JS 回调，塔/dismantle 等其他伤害源仍未接此接口。现行契约见[JS 反击策略](../architecture/mod-retaliation-policy.md)。

坐标有效、ID 唯一、索引一致、数值合法和编码上限是宿主不变量；距离、目标准入、能量价格、部件效果、伤害公式和冲突优先级是可替换玩法。若 typed 表示无法表达新规则，提供扩展表示及相应处理/投影路径，不要求作者修改 enum 或字段宽度。JS 不持有 Rust 裸指针，也不直接破坏 native 假设。

验收包 A 为“新资源生产建筑”：声明新资源、新建筑与生产配方，玩家建造并搬运产物，建筑可受击维修并参与寻路。包 B 为“规则变体”：使用不同伤害公式或移动仲裁。再写第二个同类包验证通用接口，避免验收包成为硬编码的特殊处理器。

包 A 使用公共 SDK 作为首个正式官方 JS 内容候选，进入包组合和默认/精简配置验收；不按官方包 ID 提供特殊权限或私有处理器。迁移现有玩法时同时检查原生派发、放置/建造、预检、常量、投影与保存恢复。完整默认预设的兼容门禁保持，新增包按明确预设选择启用。

## N3–N5 的契约前置

世界级规则在串行屏障执行；room/player/world 的权限和读写域可核验，不能只信作者 `parallelSafe` 声明。当前房间串行结算先保留，后续性能改造不得减少玩法表达能力。

N4 先建立数据清单：rooms/扩展字段、players/Memory/segments/CPU/通知、market、ID、namespace state、有效规则与包身份、执行停用策略及 tick。存储每个阶段只承诺已经接线的域；增加 RNG、外部输入、outbox 后加入版本和一致性门。关闭某 Mod 的处理器仍保留 schema 与规则，因此 PlanHash 单独不足以标识执行策略。

恢复区分内存错误重试、检查点重启和确定性回放。检查点先证明完整已提交版本可恢复；回放另外固定玩法时间/随机、遍历序、外部输入和玩家执行结果。不能在重放结算时重新运行玩家代码来替代输入日志。故障注入包含写数据未完成、manifest 切换前后和重启，报告所选耐久策略/RPO。

外部 I/O 使用后台域，改变玩法的响应进入有身份/顺序的输入队列；输出走提交后的 outbox，定义去重或幂等处理。JS provider 包括业务服务和存储后端，不能把 native 默认后端的便利当作禁止 JS storage provider 的理由。首次发布存储格式和网络协议时预留真实可执行的贡献入口。
