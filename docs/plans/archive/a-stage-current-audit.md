## 2. 需要优先补齐的正确性边界

### 2.1 世界与玩家持久状态仍分两次提交

`run_players` 先调用 `settle_world`。成功后，引擎的世界时间、版本、房间、市场和玩家结算状态已经发布，协调器才调用 `commit_players` 写入 RawMemory、segments，并逐玩家发送 `settle_bill`。计费命令的错误被 `let _ =` 忽略，方法仍可返回成功。

这存在两种具体后果：线程失联可能漏计 CPU 桶；以后如果在这些写入之间增加会返回错误的操作，就可能产生世界已前进、玩家持久状态尚未完整提交的状态。简单把 `settle_bill` 改为 `?` 会暴露错误，但无法撤销已经发布的世界。

后续必须在发布前准备完整候选：房间、市场、玩家结算结果、RawMemory、segments、CPU 桶、通知、事件和 ID 游标。所有可能返回错误的转换与校验先完成，再发布这一完整版本。CPU 桶权威归协调器/事务所有，沙箱提供执行结果与计费用量，避免世界提交后仍依赖线程存活来完成账本写入。

### 2.2 玩家执行中途故障缺少恢复记录

`execute_players` 在本地收集结果。Memory 注入通信失败或执行结果为 `InfraFailure` 时直接返回错误，已收集结果随局部变量销毁；`run_players` 尚未得到结果，也不会建立 PendingRound。

如果故障发生前已有玩家执行，其 V8 全局可能已经改变。再次调用会重新执行这些玩家，不能套用“重试只结算缓存、不重跑玩家”的现有保证。以上为控制流核查发现，本次没有注入线程失联来复现。

A4/P1 的恢复设计需区分：执行尚未开始、结果已确认、执行是否完成无法确认。已确认结果不得在普通重试中重跑；无法确认的任务必须阻止本轮被视为完整成功，并提供明确的放弃或 worker 重建路径。V8 全局仍不属于世界候选的回滚范围，不能通过保留结果缓存声称撤销了玩家执行。

### 2.3 恢复门与重试输入的约束不完全一致

Engine 的恢复检查只比较世界 time/generation，不检测玩家或市场的直接修改。EmbedEngine 的管理接口通过 `no_open_round` 阻止恢复期间变异，生产入口已有这层保护，但 Engine 的公开字段允许库调用方绕过它。

另外，只有 `run_players` 的失败结算缓存玩家结果和原 TickInput。`settle_external` 不缓存意图，并在每次调用时重新采样时间；简化的 `Engine::tick` 重试会再次调用沙箱。不能把这些入口都描述为原轮精确重放。

统一发布时应同步整理公开写入口及恢复契约：哪些入口重放完整候选，哪些入口允许显式放弃旧轮并提供新输入。已有[恢复出口测试](../../../crates/kk-runtime/tests/embed_tests/stage_recovery_family.rs)需随接口一起核对，不能在改变语义时只修改文案。

### 2.4 当前故障测试覆盖发布入口，未覆盖中途写回

StageCursor 在进入指定阶段时返回错误。指定 Publish 的测试因此在第一次写回前失败；它证明候选可以丢弃，并未证明发布过程中途失败能恢复。

当前 `publish_tick` 不返回 Result，也不捕获 panic；它先替换市场，再逐房写回，随后处理通知、玩家房间集合、ID、事件和时间。validate 只检查房间覆盖与顺序、ID 游标不回退、原玩家键不丢失，不是完整世界一致性检查。

后续故障注入应覆盖各类状态的准备与最终发布边界。如果实现仍需分步修改权威状态，必须证明可恢复或具备完整回滚，不能在半写回时直接返回 Err。优先把派生状态也移入候选，减少发布阶段工作。进程崩溃与磁盘恢复仍属于 E 批，本轮不能把内存提交保证扩展为持久化保证。

## 3. 建议的实施顺序

### 第一步：建立改造前的测量基线

先完成 P2 的本仓进程 CPU/RSS 采样，并补 p99、机器信息、提交、负载和采样窗口。阶段耗时沿用已有口径，另记失败尝试和重试：当前 PerfRecorder 只记录成功调用，缓存重试的投影与执行耗时为零，不能用它单独判断故障场景的成本。

这一小片不等待三引擎环境全部就绪。后续对照仍须使用同脚本、同导入地形和可核查的工作量，在 1/4/8/32 玩家档至少各做五次独立运行；官方私服接入状态单独记录。仅有本仓测量时不作跨引擎性能结论。

### 第二步：A3，建立拥有候选数据的事务

这是下一片主线代码工作的建议范围：

1. 将当前分散的 TickCandidates、SettledRooms、市场副本整合到明确拥有数据的事务容器，保留确定的房间结算顺序和 ID 分配语义。
2. 将 Working 的玩家状态与 ID 访问改为事务访问；整个 tick 共用同一份玩家候选和 ID 游标，不能按房间各复制一份后再合并。
3. 房间规则仍可使用局部短借用，但未来调用 JS 宿主回调前必须释放可能被重入访问的可变借用。用 Rc<RefCell<_>> 包装长时间持有的借用不能解决重入问题。
4. 把通知和玩家房间集合等派生结果在发布前准备好，保留公开入口的现有行为，明确后续将收口的变异接口。

本片不实现 ModVM 或扩大玩家并发。禁止用 unsafe 指针、生命周期转换绕过所有权。验收关注逐状态一致、失败后完整旧状态、重试订单 ID 稳定，以及成功后 generation 恰增一次。

### 第三步：A4，统一玩家候选与账本提交

先接入 P1 所需的最小 RunJob 预算接口，仍串行执行；随后将 RawMemory、segments 和 CPU 桶纳入事务。这样满足 A4 对预算字段的依赖，无需等完整并发调度实现。

桶算法保持单一实现，迁移时保留现有初始化配置、正常计费向上取整、负余额停跑回充、硬中断和 halt 等规则。例如 limit=20、bucket=−41 的停跑轮应回充至 −40，而不是 −21。[现有预算测试](../../../crates/kk-runner/src/budget.rs)和[停跑回归场景](../../../crates/kk-runtime/tests/embed_tests/stop_run_regression.rs)应随权威状态迁移继续验证这些行为。

删除世界发布后的 settle_bill/discard_bill 账本往返；完成玩家写回候选的准备、故障注入和完整版本发布，同时补齐执行中途故障的恢复记录。segments 的过滤与授权语义必须保持，不能借迁移顺便改变玩家 API 行为。

### 第四步：P1，启用有界并发和线程 CPU 计费

在事务与故障边界可验证后，合并 Memory 注入和执行命令，拆分派发与回收，加入期限、并发上限及 worker 故障处置。保留串行执行作为状态对照。

当前 RunEpoch 只有 tick/generation。异步回收后，同一世界版本下放弃旧轮再开新轮，可能复用这两个值；应补尝试标识，必要时结合 worker 实例标识，证明旧回执无法污染新轮。这是未来异步化的设计风险，当前逐命令独立回执通道和同步等待不能据此直接判为已经串轮。

线程 CPU 时钟在 macOS/Linux 分别验证；墙钟继续承担活性看门狗职责。计费、预算耗尽和墙钟保护的关系需要显式测试，不能仅替换 Instant 而忽略中断费用。保留 watchdog arm/disarm 的代际保护。

## 4. 本次验证与后续门禁

本次运行 `cargo test -p kk-engine -p kk-runtime`，结果为 241 个测试项通过、0 失败：kk-engine 单元测试 28、结算集成测试 205，kk-runtime 单元测试 7、嵌入集成套件入口 1。该入口内部执行多组场景，不能将其误写为只有一条业务断言。本次只新增核查文档，没有改变运行行为。

后续改变 tick 主链路时，需执行引擎、runtime、runner 相关测试及工作区检查，补针对上述故障边界的有效回归，再跑完整 screeps-ok 和既有 bot 三夹具。screeps-ok 当前地板以 [ratchet.json](../../../compat/reports/ratchet.json) 的 **1854/2914** 为准，原批次计划中的 1852 是历史值；既有通过用例不得未经登记变红或转跳过。本次没有重跑完整 screeps-ok，不把地板值当作本次套件实测结果。

bot 保持既有验收口径：tooangel/overmind 各 2000 tick、wasm 10 tick，检查硬中断和 console error。事务改造还需对比多玩家不同执行顺序下的世界、玩家、市场、ID、事件、Memory、segments 与账本状态；时钟计费差异应使用可控用量验证规则，避免把真实耗时噪声当作状态回归。
