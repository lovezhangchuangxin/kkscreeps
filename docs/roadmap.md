# 路线图

本页定义里程碑的范围与验收条件，不安排日期。先验证玩家运行时和结算机制，再完成单机玩法、开发工具、联网服务与生产部署。局部实验用于选择方案，完整系统的性能结论由端到端基准验证。

当前各组件的能力见[项目说明](../README.md)；具体机制与尚未实现的设计见[架构文档](architecture/README.md)。路线图中的目标不代表已经交付。

2026-10-12 用户暂缓性能主线，功能方向转为[常驻运行、耐久命令与可登录客户端三批](plans/service-playable-batches.md)。该目标方案推进 M2 持久化与 M3 自建客户端首片；官方客户端连接、完整多用户运营及 M5 长跑仍单独验收，不因这三批范围较小而下调里程碑要求。实际接手位置只维护在任务台账。

2026-10-11 新增贯穿 M2–M5 的[全面架构重构计划](plans/performance-rearchitecture.md)：性能全面超过固定 xxscreeps、内存更低、保持同等灵活 Mod，用户授权必要的任意改造；**同日用户收敛验收口径**——性能线锚定 50×6，开发用分钟级短窗快速迭代，扩展场景降为登记场景库随部署线执行。目标为紧凑房间存储、受控变化集、增量玩家视图和依赖调度；已有视图复用、共享块和受限房间并行切片，完整 R00–R12 范围尚未收口，状态以[接手台账](plans/mod-next-batches.md)为准。既有玩法和服务缺口继续补齐，不以重构替代功能验收。

## M0 兼容验收与工程基建

建立 Rust 与 pnpm 工作区、CI 和兼容性工具，先独立复现锁定版本的上游测试结果，再接入本项目的适配器。适配器应真正运行玩家沙箱并输出可核对的报告；这个阶段要求“能够测试”，不要求尚未实现的游戏行为通过。

真实 bot 的环境验收在固定的桩 Game 下检查模块加载、循环运行和缺失 API。它验证运行环境，不能替代后续游戏进展验收。一实例一线程的原型验证用于确认 V8 承载方式。

完成依据：[上游复现报告](../compat/reports/m0-screeps-ok-parity.md)、[适配器基线](../compat/reports/m0-screeps-ok-baseline.md)、[bot 环境报告](../compat/reports/m0-bot-missing-api.md)与 [ADR-010](decisions/ADR-010-screeps-ok-adapter-bridge.md)。报告中的数字属于该阶段。

## M1 引擎骨架

建立 kk-core、kk-schema、kk-world 的类型化数据，以及 kk-engine 的单房间结算。早期以固定指令驱动世界，随后嵌入接口接入真实结算，建立 screeps-ok 基线和回归检查。

当前通过数下限以 [ratchet.json](../compat/reports/ratchet.json) 为准，不在路线图重复维护数字。M1 的实现与验收记录见[引擎骨架方案](plans/archive/m1-engine-skeleton.md)和 [ADR-011](decisions/ADR-011-engine-skeleton.md)。

## M2 单机可玩

M2 分为两道关卡，避免把运行环境可用与完整玩法可玩混为一谈。

- **2A：沙箱与核心玩家 API。** 接入玩家运行时、CPU 预算、Memory、世界投影和核心动作；screeps-ok 通过率达到 40%。该关卡已有验收记录，见[单机可玩方案](plans/archive/m2-playable.md)和 [ADR-012](decisions/ADR-012-m2a-sandbox-runtime.md)。CPU、内存及宿主隔离的具体边界以[沙箱说明](architecture/sandbox.md)为准。
- **2B：完整玩家 API、存储与完整世界。** 补齐玩法与玩家接口，在真实负载下完成存储选型和落盘，提供可启动完整世界及机器人对手的命令。验收要求（2026-10-09 调整）：screeps-ok 通过率 ≥95% 仅作为中间检查点，≥99% 为后续覆盖目标；最终完成要求约定范围内功能全部通过验收，每个未通过/跳过用例都有明确的范围、证据和可审查理由。通过数地板只升不降，不得靠扩大跳过范围、削弱断言或随意豁免达标；真实 bot 的经济、战斗、存活及重启能力单独验收，固定世界 bot-check 不能替代。

运行协调、失败重试、双房双玩家验证和结构整理已有阶段性成果，详见[方案索引](plans/README.md)。这些成果不能替代 2B 的整体验收；固定世界 bot-check 也不能证明孵化、建造和经济链已经正常推进。

玩家 API 扩面见 [M2B 方案](plans/archive/m2b-expansion.md)。terminal 与市场已开展独立实现和验收，见[终端与市场方案](plans/archive/2b-terminal-market.md)，后续应按剩余差异补齐，不能继续把整个市场视为 M4 才开始的能力。

核心仓库搬运与分片 GCL 输入已接入；两种玩家投影分别通过连续 40 tick 的采集、容器搬运和升级守恒场景，记录见[核心经济链与 GCL](research/notes/economy-gcl-2026-10-04.md)。现已提供 [sim run](architecture/local-simulation.md) 和可复跑的采集、搬运、升级、寿命到期后孵化替补场景；真实 bot 综合验收、特殊存储规则、数据库与内容级迁移仍须继续推进；已有[检查点/JSON 载荷迁移](architecture/checkpoints.md)、[输入日志/结算回放](architecture/input-log.md)及 sim 周期保存/目录恢复。

2026-10-09 新增 [TooAngel 单房经济与冷恢复验收](../compat/README.md#tooangel-单房经济与冷恢复)：锁定的未修改 bot 在 JSON/KKPV 各完成 2000 tick 连跑与 1000+1000 tick 跨进程续跑，验证实际采集、转账、建造、升级、死亡后补员和输入回放。TooAngel 首片不包含战斗或多房，不关闭 M2B 整体验收。随后新增 [Overmind 原版单房经济与冷恢复](../compat/README.md#overmind-持续世界与冷恢复) 和 [普通 Invader 持续战斗](../compat/README.md#普通-invader-持续战斗与冷恢复)：前者通过同样的六阶段经济/寿命矩阵，后者以实际位置/hits 与事件验证 NPC 行为及 200 tick 直跑/冷恢复等值。2026-10-10 新增 [TooAngel 防御战斗与冷恢复](../compat/README.md#tooangel-防御战斗与冷恢复)：真实 bot 防御链（塔攻击/防御者出生/安全模式激活）经敌方脚本坦克在 520 tick 双通道六阶段矩阵验证；随后新增 [TooAngel 多房进攻与冷恢复](../compat/README.md#tooangel-多房进攻与冷恢复)：敌方预留触发 attackunreserve 跨房出击并击杀 reserver，经 2900 tick 双通道六阶段矩阵验证。TooAngel 长期存活已通过双通道 86400 tick 连跑、截点冷恢复与回放核对，见[机器报告](../compat/reports/gameplay-tooangel-survival/summary.json)；这是 72h 等价游戏时间，不能替代 M5 墙钟长跑。bot 对战、多房扩张运营、Overmind 旗标出兵、数据库与完整世界仍未收口。

并发调度、统一提交和共享视图遵循 [tick 契约](architecture/tick-contract.md)与[快照契约](architecture/snapshot-contract.md)。这些文档分别说明现状和目标；提出契约不等于生产通路已经完整接入。端到端基线按[性能验收方案](architecture/performance-acceptance.md)采集，须先确认夹具实际产生动作与状态变化。

## JS Mod 与架构扩展

独立 JS 包创造完整玩法、覆盖固定 xxscreeps 的十一贡献领域，是[完整玩法计划](plans/mod-complete-gameplay.md)与 [ADR-007](decisions/ADR-007-mod-system.md)约定的目标。官方内容应使用公共 SDK 形成可选包与预设；作者提供第二种同类玩法无需新增专用 Rust 分支。已有新世界[内容选择](architecture/mod-content-selection.md)，完整官方 JS 预设与内容迁移仍未完成。

目前已有自主对象生命周期/增删、新资源与建筑、部分战斗/移动策略、组合诊断、玩家类型生成，以及检查点/日志/回放和包集合切换。默认动作有消费者不等于对应策略可由 Mod 替换；完整移动仲裁、生产动作、跨房/账户/世界规则和服务/客户端贡献仍有缺口。每个父项与子片的实际状态只维护在[接手台账](plans/mod-next-batches.md)，接口通过[架构索引](architecture/README.md)查询，逐批沿革见[历史记录](research/notes/roadmap-history.md)。

[ADR-014](decisions/ADR-014-contribution-plane.md)要求扩展基础随玩法与服务接线；新增写域当片提供保存恢复和版本策略。拒绝、异常、超时、停用、冷恢复及组合顺序须分别验收，不能用少数样例或默认玩法通过率代替全领域开放。性能改造须保留合法 Mod 的通用/有序执行路径，具体约束见[总体架构](architecture/overall.md#性能改造与-mod-扩展能力)。

## M2.5 开发套件

实现 `kkscreeps sim / test / watch / deploy`，设计见[开发套件](designs/dev-kit.md)。场景、断言与世界推进应使用和服务器一致的运行及结算通路，使玩家能复现错误并验证自己的代码。

当前 `sim run` 已接入版本化 JSON 场景（含世界 seed，玩法随机/时间协议见[确定性玩法时间与随机协议](architecture/gameplay-determinism.md)）、多玩家模块、初始 Memory、最终状态断言和报告，见[交付记录](research/notes/sim-run-2026-10-04.md)。显式检查点保存/冷恢复与 sim 续跑已接入。独立的 `init/watch/replay/test/deploy` 通用开发命令、内容级迁移与自动更新尚未实现；已有 `mod init/test/inspect/types` 和 JSON 检查点载荷显式迁移链。结算回放核对已由 `sim run --verify-replay` 提供（G25.b），任意 bot 的服务器级确定性回放仍属后续。

验收目标是固定场景中上千 tick 的集成测试秒级完成。报告须记录玩家代码、世界规模、构建配置、预热与耗时，不能把这个目标理解为任意 bot 或任意世界的耗时保证。当前部分 CLI 命令仍为占位入口，接口名称存在不代表工具已经完成。

## M3 网络、客户端与多用户

实现认证、账号、代码上传、房间订阅与控制台等核心 HTTP/sockjs 接口，使多个玩家在同一世界运行。市场端点随已有引擎能力接入，避免用空壳端点代替玩法。

自建客户端采用 Vue 3、自研渲染器和共享包，见[前端架构](architecture/frontend.md)。`apps/game` 仍占位，独立 renderer 与部分共享类型已实现；客户端常量/DTO 生成管线、构建产物嵌入和发布流程仍属交付范围。房间观战先行，世界地图、回放与市场视图可在 M4 补齐。

G27.a 已有独立后台线程/V8 和只读探针；耐久输入/outbox、provider、HTTP/WS 与客户端闭环仍待实现。验收须实际登录、上传代码、订阅房间并读取控制台，核心端点冒烟测试全部通过。官方客户端另做连接与协议验证，不能从玩家 API 通过率推导可连接；素材与发布条件也应按前端文档核实。

## M4 完整玩法与扩展

19 个 power 默认消费者已接通，本地 InterShardMemory 与 CPU shardLimits 已有入口；剩余包括真实跨 shard 行为/通信、官方世界导入、地形生成及市场和其他玩法差异。完善 Mod 的服务及客户端能力、回放和历史界面，并根据负载需要实现多机部署后端，见[存储架构](architecture/storage.md)。

验收要求是全功能对照官方可玩并完成负载基准。后端选型不能自动证明跨进程原子提交、失败恢复或全域事务已经成立，相关故障场景必须单独验证。

## M5 生产化

按[性能验收方案](architecture/performance-acceptance.md)发布与官方及 xxscreeps 的正式对照报告，保留统一场景、正确性结果、原始数据和资源指标。

2026-10-10 用户将近期性能工作前移，限定为 50 玩家×6 个 RCL8 满功能成熟房这一组；成功条件为比 xxscreeps 更快且内存更低，2GB 改为参考目标。共同初始夹具和真实活动须验证，尚未完整玩法产生的有限差异量化披露，逐位等价另作为严格排错选项；此局部引擎对照不代表 M3/M5 服务和长期运行验收完成。

上述单组限制经 2026-10-11 全面目标扩展后同日收敛：最终以 B0 长窗（500+3000×2）+ 等价收尾验收，登记场景未执行项挂账移交部署线，不能只凭一次成熟房短窗宣布整体领先；2GiB 仍是容量参考档。比值目标仍是工程验收线，不能把某个短窗收益标成完整目标已达成。

进行至少 72 小时的长跑，观察内存趋势、任务与句柄积压、延迟及故障恢复。验收要求内存稳定、没有已检出的泄漏；一次长跑不能证明所有路径都不存在泄漏。

公网部署前完成进程隔离、资源限额、内部宿主接口复查与恢复验证。seccomp 等平台机制须按部署系统选择，具体边界见[沙箱说明](architecture/sandbox.md)，不能把单进程开发环境直接视为公网安全方案。

## 验收原则

Mod 后续工作使用[30 项任务与接手台账](plans/mod-next-batches.md)维护当前执行位置、依赖、实际验收和剩余范围。AI 接手及每批结束主动更新台账，并将里程碑变化同步到本路线图；架构契约仍以 architecture 为准。

执行按台账的子片队列而非父编号串行：作者工具/类型、覆盖审计及默认参考前置；新增写入域当批补齐保存恢复；持久输入/outbox 与存储的原子发布一并验收。M3 最小网络与客户端是实际开发工作，不是默认已就绪的 Mod 前置。覆盖台账有遗漏时继续拆片，不以现有 30 个父任务的首片完成代替 M4/M5 收口。

合入须通过适用的格式化、静态检查、测试和文档链接检查。当前 CI 另有完整 screeps-ok 回归任务，见[工作流](../.github/workflows/ci.yml)。新增生成管线时，应一并接入生成物新鲜度校验；常量与 DTO 的完整校验仍是交付要求。

兼容性验收同时检查通过数下限和逐用例回归，失败预期与回归豁免分别管理；不得靠扩大跳过范围提高通过率。偏差须按[兼容性要求](designs/compatibility.md)记录触发条件、可观察影响和验证依据。功能、bot、客户端与性能验收分别提供证据，不能相互替代。

历次批次、数字沿革与修订记录保存在[路线图历史记录](research/notes/roadmap-history.md)。历史记录按当时的实现理解，当前状态须核对源码与新报告。
