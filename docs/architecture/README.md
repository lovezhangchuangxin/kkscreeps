## 一页概览

```
                    ┌─────────────────────────────────────────┐
                    │           kkscreeps（单个可执行程序）        │
                    │                                         │
  玩家浏览器 ←─ 网络 ─┤  backend（HTTP + WebSocket，兼容官方协议）  │
                    │       │                                 │
                    │  ┌────▼─────────┐    ┌───────────────┐  │
                    │  │ 游戏引擎       │    │ 玩家代码沙箱    │  │
                    │  │ 房间结算/移动/  │←──→│ deno_core(V8) │  │
                    │  │ 战斗/市场      │    │ 每用户一个实例   │  │
                    │  └────┬─────────┘    └───────────────┘  │
                    │       │                                 │
                    │  ┌────▼─────────┐                       │
                    │  │ 存储层        │  内存为主，定期写盘       │
                    │  └──────────────┘                       │
                    └─────────────────────────────────────────┘
```

与官方服务端最大的不同：官方是 5 个以上 Node.js 进程加 MongoDB、Redis 两个中间件，进程之间所有数据都要经过 JSON 文本序列化；我们把整套系统放进**一个程序**，数据在内存里以二进制形式直接传递，需要持久化时才写盘。

## 设计原则

1. **玩家看到的世界和官方完全一致**（约束见 [docs/designs/compatibility.md](../designs/compatibility.md)）。所有优化只发生在玩家看不到的内部。
2. **一个房间是一等数据单元**。房间的全部状态编码成一段连续的二进制数据（下称"房间快照"），读、写、传给沙箱、写盘都以它为单位。这让各个模块之间传递数据时不需要反反复复做对象和文本的转换。
3. **能不复制就不复制**。玩家代码读游戏对象时，直接从共享内存里按位置读取，而不是把整个房间的数据复制一份进沙箱。
4. **默认单进程**。单机部署就是一个进程；两种情况下会拆分：面向公网的生产部署可把承载玩家代码的进程按组拆开（坏一个进程不波及全局，见 [sandbox.md](sandbox.md) 的安全边界）；要跨机器扩展时，通过统一的存储接口接入 Redis 或 FoundationDB，而不是一开始就背上分布式复杂度。
