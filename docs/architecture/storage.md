# 存储与数据传输

当前游戏状态保存在内存世界中。`kk-storage` 已提供本地文件持久化原语（现行能力）：带哈希的有界信封读取与错误分类（撕裂/校验值不匹配可跳过；I/O 故障、超限、未来格式必须停止）、原子发布（同目录临时文件 → 写入 → 文件同步 → rename → 父目录同步）与目录单写者租约（固定 inode 锁文件上的 OS 独占锁，进程退出即释放）；不解释游戏规则、不依赖 runtime/V8，数据库后端仍无。`kk-backend` 仍为预留模块，没有数据库写入、HTTP 监听或 WebSocket 推送。现有 runtime 已提供显式单文件[检查点保存/冷恢复](checkpoints.md)（含房间、玩家、市场和 Mod 状态）、[输入日志](input-log.md)与 sim 级[周期保存与恢复选择](checkpoints.md#周期保存与恢复选择g26a)（本地文件），以及服务状态目录基座（[服务目录检查点](checkpoints.md#服务目录检查点s11)）。本页其余部分区分现行表示与数据库/共享快照/网络层的目标约束。

## 现有数据表示

| 数据 | 当前处理方式 |
|---|---|
| 房间与对象状态 | `kk-world::RoomState` 及类型化对象，供查询和结算使用 |
| 二进制房间快照 | `kk-schema` 顺序编解码，整数采用小端；编码不自行写盘 |
| 玩家可见世界 | JSON 通道由 `kk-world::world_json` 投影；KKPV 通道使用二进制房块、公开地形共享束和逐玩家信封，由协调器注入 V8 |
| 查询结果 | `kk-world::snapshot` 生成对象 JSON，字段和缺省值与沙箱数据不同 |
| 玩家指令与写回 | 沙箱导出 JSON，宿主清洗后交给结算或作为提交候选 |
| RawMemory 与 segments | 成功结算后更新，可随完整检查点保存；单独跨 tick 保留不等于自动写盘 |

KKPV 的共享资格、旧读者生命周期与解码边界见[快照契约](snapshot-contract.md#当前版本与编码边界)。它不是向所有沙箱共享完整权威世界；市场/power 等仍由逐玩家信封注入，没有完整的增量订阅通道。具体执行边界见[总体架构](overall.md)。

## 共享快照目标

目标是将已提交房间编码为不可变字节，并使玩家视图与检查点绑定同一世界版本。检查点保存完整权威状态，沙箱只接收已授权的公共字节和私有视图；不能因房间可见就向玩家暴露完整载荷。类型化对象用于构造与结算，不能将 Rust struct 的进程内布局直接作为磁盘格式。

当前持久房间 schema 宏只为连续的简单定长字段前缀生成偏移；嵌套或变长字段之后不再生成偏移。KKPV 已有自己的对象目录、列编码、变长区和共享句柄，但仍解码装配；权威内存页、列式 getter 共享直读及检查点增量格式仍是目标，要求见[快照契约](snapshot-contract.md)与[目标架构](performance-target.md)。

结算生成新逻辑版本，旧读者释放前必须保留旧版本。双缓冲不能被理解为无条件循环覆写两个内存槽；固定版本的数量、字节数和慢读者处置都需要限额与测量。

二进制指令、市场增量、共享地形和 Memory 局部重编码是减少复制的候选方向。实现时还须保持玩家可见行为、视野权限和计费契约；没有访问某字段不代表当前已免除该字段的投影、传输或解析成本。

## 检查点现状与后续目标

当前单文件检查点的信封版本为 1，JSON 载荷版本为 9；文件同步、rename 替换后同步父目录，规则/包身份和停用掩码随之核验。显式保存之外，sim 级周期保存、输入日志与 JSON 载荷显式迁移链已交付；数据库、内容级迁移及房间二进制历史迁移仍无。详细数据清单、故障边界和 CLI 示例见[检查点契约](checkpoints.md)。以下是多文件/数据库与后续恢复要求。

检查点须保存一个完整的已提交世界，包括房间集合、玩家状态、市场状态、随机输入或种子、全局 ID 游标以及对应版本。仅将各房独立的最新文件拼在一起，可能形成从未提交过的世界。

目标流程为先写候选数据、校验并完成所需持久化，再原子发布 manifest。manifest 明确引用每项数据的版本和校验值。文件替换的原子性、数据库提交和断电后的持久性是不同保证，须按平台及引擎配置验证。

周期检查点只承诺恢复到最后完整保存的版本，丢失窗口按实际保存间隔报告。现行输入日志 v2 保存玩家 Memory 摘要，不能用结算回放重建日志尾的完整玩家状态；sim 目录恢复核验日志游标后回滚到检查点、原子截断未确认后缀，并将丢失拍并入新运行重新执行玩家代码。结算回放则直接消费已记录输入、核对世界及 Memory 摘要，两者用途不同。守卫和失败边界统一见[周期保存与恢复选择](checkpoints.md#周期保存与恢复选择g26a)及[输入日志](input-log.md#目录恢复v2回滚-截断-重执行)，不能宣称 RPO=0。CLI 没有默认保存间隔。

版本格式一旦发布，布局变化必须提供旧版读取、升级、校验与重新写入路径。当前升级接口不等于已有完整历史迁移和崩溃恢复实现。

## 存储引擎选型

`kk-storage-bench` 在合成房间、玩家记录和大字节块上比较 redb 与 libmdbx，按 feature 启用相应引擎。基准方法与历史结果见[存储基准记录](../research/notes/storage-bench.md)，决策依据见 [ADR-008](../decisions/ADR-008-runtime-model.md)。

微基准需明确事务提交是否包含同步写盘、读取是否受缓存影响。正式选型还需验证真实工作负载、检查点一致性、损坏输入、恢复时间与平台支持；当前尚未将任一候选接入游戏持久化。

跨机器部署还需定义版本发布、消息确认、失败恢复与分布式原子性。替换成 Redis 或其他后端不会自动获得与单机相同的提交保证。

## 网络层

目标网络层提供登录、代码管理、世界查询和订阅推送，并对照官方 HTTP 与 sockjs 协议验证。axum 是目标技术方案，当前 `kk-backend` 尚无实现，因此不能承诺现有客户端已经可以直接连接。

提交后的变更集可用于减少订阅数据重读与比较。实现前须定义初始快照、增量顺序、漏包重同步、背压和按订阅者视野过滤；候选状态不能在世界提交前推送。网络投影也不应直接暴露内部快照字节或宿主句柄。

完整系统的开销与收益按[性能验收](performance-acceptance.md)测量，研究中的单项数字不能替代持久化和网络工作的端到端结果。
