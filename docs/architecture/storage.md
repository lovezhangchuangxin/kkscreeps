# 存储与数据传输（kk-storage）

官方栈有明显的数据传输与写放大开销：多个进程之间经 JSON 文本传输，私服版把热数据放在一个文档里定期整体写盘。本模块的目标是减少这类开销；具体收益按[端到端性能验收](performance-acceptance.md)测量。

## 核心数据单元：房间快照

一个房间的已提交状态目标编码成一段**连续的二进制数据**，称为房间快照；玩家持久状态、全局 ID 与检查点 manifest 另行记录。参考 xxscreeps 公布的数值（其项目文档：普通房间 250 字节到 60KB；一堵墙 44 字节；一个满配 50 部件的爬爬虫约 274 字节）；本项目的真实尺寸须在 M2 布局原型与基准中报告。格式、生命周期和恢复边界见[快照契约](snapshot-contract.md)。

快照格式的要点：

- **布局由 schema 生成**：固定宽度字段按类型与列偏移直读；字符串和数组经长度描述符惰性解码。M1 的 `kk_schema!` 当前只生成定长前缀偏移，不能把它当作完整共享视图布局；
- **字段设计让零值常见**：大多数字段大多数时候是 0（比如用"非激活标志"而不是"激活标志"），新房间几乎全是零字节；
- **版本化与升级**：首次持久化格式发布后冻结版本；布局改变须提供旧版读取、升级、重新写入和损坏输入测试。M1 当前只有升级链挂载点，尚无历史版本迁移。

## 双缓冲：读写不冲突

玩家代码读取已提交的不可变版本，房间结算构造候选新版本；所有房间与玩家持久状态验证成功后一次发布。相邻版本逻辑上构成双缓冲，但旧版本仍被慢沙箱固定时不能覆写其物理内存。没有变化的休眠房间可沿用旧句柄；代际保留、内存上限与旧对象引用行为见[快照契约](snapshot-contract.md)。

## 传输：能共享就不复制

| 数据 | 传输方式 |
|---|---|
| 房间快照 → 沙箱 | 目标为共享内存直读；约 2 纳秒仅指原始字段的孤立微基准，完整 getter/tick 另测 |
| 全图地形表 | 一份只读共享内存，所有玩家实例共用，不重复占用 |
| 市场订单/用户名/交易/事件日志 | 增量通道：只传变化的部分和该玩家没见过的部分 |
| 指令（intent）流 | 二进制编码（官方是 JSON 文本），编码耗时按第三方基准推算约降一个数量级（rkyv 与 JSON 的公开对比约为 14 倍差距，非本项目实测） |
| 玩家存档（Memory/RawMemory） | 以 UTF-16 编码常驻共享内存，玩家代码首次访问才解码，tick 末只重编码被修改的部分 |

最后一条值得展开：官方每 tick 把玩家存档整个做一次"JSON 文本 → 对象 → JSON 文本"的往返（实测 106KB 存档约 9.2 毫秒，2MB 存档外推约 180 毫秒），而且这段时间计入玩家自己的 CPU 账单。我们的方案下，玩家没动过的部分一个字节都不用重新编码。注意：省下的是服务器侧的开销，玩家账单不降——计费仍按官方等价工作量虚拟收取（见[兼容性红线](../designs/compatibility.md)）。

## 磁盘持久化：内存为主，定期检查点

写盘策略是"**热数据全部在内存，每隔一段固定时间（默认约 2 分钟，采纳 xxscreeps 的默认值）把变化的房间快照写盘**"，而不是每 tick 都写：

- 写盘引擎在 redb 与 libmdbx 之间选择（两者都是嵌入式单文件键值库，前者纯 Rust，后者更成熟），按房间名分键、按数据类型分表。选型时机：M1 不接真实存储引擎（内存 + 简单文件导出即可），M2 做基准对比后定（[ADR-008](../decisions/ADR-008-runtime-model.md)）；
- 只用定期检查点时，崩溃恢复会丢失最近一个完整检查点之后的进度。检查点以包含全局状态版本的 manifest 原子发布，防止混用不同 tick 的房间。接近零丢失需要额外的持久意图/玩家状态日志及顺序保证，尚未实装；
- 官方私服的对照：解包其闭源存储组件证实，它是把所有热数据放在单个文档里、每 10 秒全量序列化重写，按 100 用户/50 活跃房推算每 10 秒要整体重写 40~110MB——与社区报告的"私服 CPU 莫名爬满"现象吻合（推断的根因，总量按假设规模推算）。我们按房间增量写盘后，每次只写变化部分（通常 KB 级）。

## 跨机器扩展（后期）

单机形态下存储就是"内存 + 检查点文件"。将来需要多机时，定义统一接口（读写房间快照、发布订阅消息、计数器），第一个分布式后端对接 Redis（和单机版共用同一套原子语义），规模再大考虑 FoundationDB。引擎代码不感知后端差异。

## 网络层（kk-backend）

对客户端的协议**原样兼容官方**，社区现成的客户端、工具、官方渲染器（renderer，开源且含全套美术资源）可以直接连：

- HTTP 接口：登录认证、代码上传、市场查询、地图统计等（对照官方接口逐个实现）；
- WebSocket 推送：兼容官方的 sockjs 协议和订阅格式（sockjs：官方客户端使用的 WebSocket 兼容库及其通信协议）；
- 推送方式做了优化：官方每 200 毫秒把订阅房间的数据**整个重读一遍**再对每个订阅者做一遍深比较；我们直接把房间结算时天然产出的"变更集"按订阅者的视野过滤后推送（KB 级的变更集，量级为调研估算），两边的全量读和重复比较都消失。

技术选型用 axum（Rust 社区主流的 Web 框架，出自 tokio 团队）。
