# 玩家代码沙箱（kk-runner）

玩家上传的是 JavaScript 代码，在服务器上运行且**不可信任**——它可能写死循环、可能试图读文件、可能恶意耗尽内存。沙箱模块负责：安全地运行这些代码、精确限制它们能用的 CPU 时间和内存、把游戏世界呈现给它们、把它们的指令收回来。

## 选型：deno_core（V8 引擎）

采用 [deno_core](https://crates.io/crates/deno_core)（Deno 团队维护的 V8 嵌入库，V8 就是 Chrome 浏览器和官方 Screeps 用的同一个 JavaScript 引擎）。选它的理由（有实测或生产先例支撑，置信级别见 [沙箱选型报告](../research/02-sandbox-evaluation.md)）：

1. **和官方完全相同的引擎**：玩家代码的语法兼容性、执行性能、行为细节天然一致；
2. **CPU 时间与内存都能精确限制**：超时强制中断、内存超限强制回收都实测通过（下面详述）；
3. **有生产先例**：Supabase 的边缘函数服务用同样的方案跑大量不可信代码（每实例 256MB 内存、2 秒 CPU 上限）。

曾经评估过的候选（QuickJS、Boa 纯 Rust 引擎等）及淘汰原因见 [决策记录](../decisions/)。

## 每个玩家一个独立实例

每个玩家分配一个独立的 V8 实例（isolate，V8 内部的隔离运行环境），**跨 tick 持久保留**：玩家模块的缓存、全局变量（`global`）在 tick 之间不丢失，这正是官方的行为（玩家依赖它来做跨 tick 缓存）。只有三种情况会重建实例：玩家更新了代码、玩家内存超限或自杀（`Game.cpu.halt()`）、闲置太久。

线程与实例的管理分三层，避免混淆（详见 [ADR-008](../decisions/ADR-008-runtime-model.md)）：

- **要不要跑代码**：跟官方一致——每 tick 执行所有注册用户的代码（预算桶耗尽的跳过）。注意"没有任何世界对象"的玩家不能跳过：他们仍可写 Memory、生成 pixel，跳过会被观察到；
- **要不要处理房间**：跟官方的"活跃房间"一致——有玩家对象或本 tick 收到指令的房间才结算，其余休眠；
- **要不要保留实例/线程**：纯资源管理，玩家不可感知。每玩家一个专属线程，玩家空闲时线程挂起（park，常驻开销仅几 KB）；V8 实例沿用官方的 3 分钟空闲销毁（重建实测不到 1 毫秒、约 2MB 内存）。

配额上的硬数字（与官方一致）：单个实例内存上限约 256MB，玩家原始存档（RawMemory）上限 2MB，内存分段（segments）每段 100KB、同 tick 最多激活 10 段。

## CPU 限制：预算桶（bucket）机制

CPU 不是死板的 20 毫秒，而是官方那套"预算桶"经济（已用 24-tick 仿真完整验证）：

- 每个玩家有一个桶，每 tick 自动充值 20（`Game.cpu.limit`），桶的容量上限 10000；
- 本 tick 可用时间 = min(500, 当前桶余额 + 20)，这就是玩家读到的 `Game.cpu.tickLimit`；
- 用不完的时间留在桶里攒着，忙的时候可以透支桶一次跑几百毫秒；
- **超时的瞬间，一个监督线程强制掐断正在执行的代码**（不管它执行到哪），按整份预算计费。桶还够（扣完不为负）时下一 tick 照常执行；只有把桶扣成负数（透支）时，下一 tick 才停跑一次，停跑期间桶继续回血，回正后恢复执行（不会无限期卡死）——官方 `cpuAvailable` 语义，官方的 skipTicksPenalty 是 runtime 进程硬重置专用，不用于普通超时；

实现分工：掐断用 V8 的跨线程终止接口（实测在预算处精确生效，之后实例可以继续复用）；计时读操作系统的线程 CPU 时钟（纳秒精度）。玩家代码里随时调用 `Game.cpu.getUsed()` 查询已用时间——宿主函数调用的实测开销约 5 纳秒一次（简单参数的快速调用路径），`getUsed()` 属同一形态、量级相同（未单独计时）。两个实现期必须遵守的纪律（实验踩坑记录）：看门狗要带"代际"守卫，防止上一个 tick 迟到的掐断信号误杀下一个 tick；每个 tick 开始前先清除遗留的终止标志。

## 内存限制

组合两道闸门（缺一不可，这是实验踩出来的坑）：先给 V8 实例设堆上限，再注册"接近上限"回调，在回调里优雅终止代码。只设上限不注册回调的话，V8 会直接崩溃整个进程（实验中复现过，进程以错误码 133 退出）。

玩家代码用 WebAssembly 时，其线性内存不受上述堆上限约束，需要额外给缓冲区分配设上限——已列入实现期的安全清单。**TypedArray 的 backing store 同属堆外内存**（`new Uint8Array(270MB)` 可成功分配且不触发 near-heap 闸门，第八轮评审实证）——官方 ivm 的 memoryLimit 同样不覆盖它（官方玩家也可这样分配），因此这不是玩家可见差异，而是资源治理缺口：每 isolate 的 backing store 计量与限额归入 M5 安全加固（与 wasm 线性内存上限同批）。在多玩家共进程的 M0~M2 阶段，其兜底是看门狗（分配后的持续写循环会被掐）与按组拆进程的部署边界。

## 玩家怎么"看见"游戏世界

这是性能上最重要的设计。官方的做法是每 tick 把玩家可见的全部世界数据**复制一份**塞进沙箱（包括整本市场订单簿、交易历史，哪怕玩家根本不看市场）。我们的做法：

1. 目标是把已提交的**房间快照**作为不可变共享视图提供给有权限的沙箱；布局与代际规则见[快照契约](snapshot-contract.md)；
2. 沙箱内的游戏对象是一个薄壳：固定宽度属性从共享字节读取，字符串与数组惰性解码；约 2 纳秒只对应原始字段读取的微基准；
3. **玩家没访问到的数据就永远没有代价**——没碰过的爬爬虫部件数组不会进 V8 的内存，不给垃圾回收添负担；
4. 世界级数据（市场订单、用户名、交易记录）走增量通道：只传这一 tick 变化的部分和玩家没见过的部分。

tick 结束后，包装器按对象 ID 在当前已提交代际重新定位，不保留可能被覆写的旧偏移。对象底层已销毁时，旧引用的访问将失效；**对象仍存活时，玩家缓存的旧引用可继续读写**——这是官方实测语义（screeps-ok 27.12 缓存活引用用例以上游 vanilla 为基准）。具体 getter 行为须由对照测试锁定。

## 多模块代码与热路径计算

- **模块系统**：玩家上传多个 CommonJS 模块（`require` / `module.exports`），沙箱内提供约 50 行的加载器。已验证的语义：循环依赖（拿到半成品导出对象）、模块缓存跨 tick 命中、全局状态跨 tick 持久、模块执行失败删缓存重抛（下一 tick 重跑自愈）；边角语义（如模块内 `this === module.exports`、循环依赖半成品导出）按 Node 语义实现并单测锁定——与官方行为的差异已在[兼容性红线](../designs/compatibility.md)灰区表登记，M2 玩家 API 层对照拍板。`main.js` 的 `loop()` 是每 tick 入口。全局提供 lodash 3.10.1（`_`），与官方相同。
- **原生计算注入**：寻路等重计算由 Rust 完成，以函数形式注入沙箱供玩家调用。调用开销分两档：简单参数的快速路径实测约 5 纳秒一次；带数据缓冲的调用（如寻路传入成本矩阵）走较慢的路径，实测约 0.2 微秒一次——两者相对毫秒级的计算本身都可忽略。`PathFinder.search` 的 `roomCallback` 回调——官方设计里搜索算法会在展开每个新房间时回调玩家代码要一份通行成本矩阵——已验证可以完整复刻（回调约 38 纳秒一次，返回"成本矩阵 / false 拉黑该房间 / undefined 用默认"三种值；回调里抛异常会终止搜索并把错误消息传回玩家——与官方"原样重抛异常对象"还差一层包装，1:1 对齐列入实现期事项）。
- **启动加速**：游戏运行时的常量、类定义预先固化进 V8 快照（snapshot，引擎的序列化启动机制），新实例创建从约 3.4 毫秒降到约 0.8 毫秒。

## 安全边界

- 沙箱默认没有文件系统、网络、进程访问能力；
- deno_core 自带的一组内部函数（`Deno.core`，及挂有同一 core 对象与 internals 的 bootstrap 命名空间 `__bootstrap`）默认对玩家可见，启动时必须遮蔽——M0 已实装（删除两个全局 + 沙箱测试做 `getOwnPropertyNames` 全局面白名单比对，deno_core 升级若新增残留全局，测试显形）；
- 同一进程里的多个实例之间不是硬隔离（V8 的固有边界），所以面向公网的生产部署按组拆分进程：每个进程只承载一组玩家实例、不持有密钥和数据库连接，坏一个进程不影响全局（Supabase 同款做法）；Linux 上再加系统级的 seccomp 限制（Linux 的系统调用过滤器）；
- V8 引擎的安全补丁跟随 deno_core 的发版节奏（我们不能单独升级 V8 版本），运维上需要锁定版本 + 定期升级 + 安全事件驱动的应急流程；
- 常量表固化进快照后有一个细微的语义差异：玩家修改常量对象（`C`）在官方是静默复位，冻结后可能变成静默失败——是否可观察待行为测试套件验证（已列入兼容性检查）。
- 实例的销毁有顺序要求（必须按创建的逆序销毁，V8 的硬性约束），玩家生命周期管理据此设计。
