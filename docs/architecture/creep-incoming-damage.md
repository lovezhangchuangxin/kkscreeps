# Creep 受击结算与强化 TOUGH

2026-10-06 已实现原生 TOUGH 减伤，作为统一受击策略的第一片。当前公式仍由 Rust 执行，JS 替换受击公式、护盾或免疫的独立槽尚未开放。

## 结算顺序

原生近战、单体/群体远程、塔、原生反击与 JS 单体/批量伤害、显式反击，均向 creep 的待伤害队列累计**减伤前伤害**。攻击动作不立即改动目标 hits/body，事件中的 `damage` 仍是动作登记的原始量。结构仍立即扣耐久、必要时转成废墟，结构没有 TOUGH 减伤。

目标的对象 tick 在移动、寿命与疲劳处理后，按以下顺序结算：

1. 取当轮累计待伤害和待治疗。
2. 按受伤前 body 的顺序计算 TOUGH 总减伤量并取整，得到实际扣血量。
3. 从原 hits 扣实际伤害，再加累计治疗，钳到 body 长度 × 100。
4. 最终 hits ≤ 0 才死亡并生成墓碑；净变化才从身体尾部重分配耐久；净减少才按剩余活跃 CARRY 容量掉落超量资源。

同轮治疗能救回扣伤后瞬时为负的 creep，但不能提前修复 TOUGH、增加本轮减伤额度。移动疲劳恢复仍读取受伤前活跃 MOVE；下一轮身体效能与减伤读取本轮最终部件耐久。原有寿命到期、孵化和移动处理的提前退出规则继续生效。

## TOUGH 公式

算法依据固定上游 `@screeps/engine` 的 `src/processor/intents/creeps/tick.js` 中 `_applyDamage`，强化比例来自 `kk-core::constants::BOOSTS`：GO 0.7、GHO2 0.5、XGHO2 0.3。

对每个部件，设现有耐久为 `h`、承伤比例为 `r`（未强化/无有效 damage 强化为 1），剩余原始伤害为 `d`：

```text
本部件承伤额度 = min(h / r, d)
本部件减免 = 本部件承伤额度 × (1 - r)
d -= 本部件承伤额度
实际扣血量 = 原始整数伤害 - round(各部件减免之和)
```

已毁部件额度为零。未强化部件仍消耗排在它后面的护甲之前的伤害；超出所有部件额度的伤害全额扣血。对整轮总减免取整一次，不能对攻击逐次取整或对每件护甲分别取整。例如 GHO2 承受两次各 1 点伤害，累计减免 1、扣血 1；按每次独立取整会错误地扣血 0。单轮 45 点伤害减免 `round(22.5)=23`、扣血 22。

实现保留原始 i64 伤害，仅减伤额度使用浮点计算；大额伤害不会因整值转成浮点再转回而丢失低位。没有新增队列或持久化字段。

## JS 作者与恢复边界

`applyDamage`、`applyDamageBatch` 和 `setRetaliation` 的 amount 均表示减伤前数值。2026-10-06 之前宿主尚未实现 TOUGH，本片开始对强化 TOUGH 应用默认受击公式。未强化 TOUGH 仍按 1 承伤；已有示例的“按活跃 TOUGH 数量计算护甲”是 JS 自定公式，若同时给身体强化 TOUGH，会叠加默认减伤。当前没有绕过或替换默认减伤的 JS 写能力。

这不改变攻击策略的距离、阵营、安全模式和 rampart 改向边界，详见[单体伤害](mod-damage-policy.md)、[群体伤害](mod-mass-policy.md)和[反击表](mod-retaliation-policy.md)。反击仍在攻击动作阶段预计算，不能据对象 tick 后的实际净伤害量自动按比例反弹。

链正常拒绝恢复减伤前队列；TOUGH 在成功动作全部结束后计算。整轮写回失败丢弃已减伤的候选，重试从已提交身体重新计算，沿既有玩家缓存、Memory/Mod state 提交边界恰一次发布。检查点只保存已提交身体/boost/hits；恢复后直接用其剩余耐久，不额外保存护甲缓存或重复应用旧伤害。
