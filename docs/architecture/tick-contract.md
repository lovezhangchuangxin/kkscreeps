# Tick 调度与提交契约

本文定义玩家运行结果、世界结算和提交的约束，并描述并行房间调度的目标。当前执行路径见[游戏循环](game-loop.md)，设计依据见 [ADR-013](../decisions/ADR-013-architecture-review-coordinator.md)。下文的任务依赖、RoomPatch 合并和检查点要求尚未完整实现。

目标调度要求房间同时满足输入就绪与共享语义依赖就绪，ID/账户操作不得仅通过末尾排序恢复语义；临时 ID 不是默认方案。早结算的 now_ms 采样及失败生命周期见[新目标架构](performance-target.md)，以下现行实现描述不因此改变。

本节 2026-10-11 修订：依赖图语义取代早前"工作阶段临时 ID + 末尾固定顺序合并"的目标方案（旧方案降级为"ID 在合并前不可被规则/Mod 观察时的待验证优化"），演进依据见[ADR-020](../decisions/ADR-020-incremental-world-runtime.md)；两版目标方案均未完整实现。同日已落地受限并行房间结算（资格门与回退契约见下文"当前实现与保证范围"），不改变依赖图目标本身。

## 当前实现与保证范围

`kk-runtime::EmbedEngine::run_players` 有界并发派发、回收玩家结果，`kk-engine` 处理房间及市场候选：满足资格门（结算工作者数 ≥2、随机派生可用、无 ClaimController 意图、无 JS 宿主贡献槽）的轮次把房间结算按块并行、市场与跨房尾段仍在主线程串行合并；不满足或任何回退走整段串行，两路径逐房间输出等价，串行路径是对照基线。RunJob 合并内存注入和脚本执行，并携带宿主从已提交玩家状态制定的 CPU 预算。沙箱返回用量；协调器计算 CPU 桶候选，与 RawMemory、segments 一起在校验阶段合并到玩家候选，再与世界和市场一起发布。发布后没有计费通信、数据库写入或网络发布。

RunJob 回执同时匹配世界 tick/generation、执行尝试编号和工作者编号。线程重建时分配新工作者编号，同一世界版本下的旧尝试或旧线程回执也会被拒绝。runner 提供独立待收回执句柄，嵌入式入口使用本轮独有的完成通知通道补充空闲槽位。回执完成时间超过命令绝对期限时拒收，未完成命令到期后不再等待；下一轮不会复用旧回执通道。`RunEpoch` 定义在 kk-core；诊断 Tick 通道也回带世界 JSON 的 time/generation，缺省字段为 0，不能替代宿主显式绑定的 RunJob 版本。

正常用量由 macOS/Linux 的线程 CPU 时钟计算，从世界注入开始，包含入口及写回计算，再加指令费用；内存初值注入与排队不在正常计费区间。其他平台明确报不支持，不回退为墙钟计费。墙钟看门狗保留原预算和代际保护，硬中断仍计完整预算。命令默认期限为派发时刻加 tickLimit（至少 1 ms）再加 1 秒通信余量；调用方可自定义绝对期限。该余量不增加玩家脚本的墙钟执行预算。

引擎的 `OwnedTickTxn` 拥有本轮输入、房间、市场、事件以及共享玩家候选和 ID 游标。共享玩家候选与 ID 游标收在 `Arc<Mutex<SharedState>>`：串行路径以短借用进出，并行路径由工作者短暂加锁进入，GCL/power 等可交换累计在锁内完成；ID 分配、游标回退、claim 等不可交换操作会标记 `serial_only`，由协调器按耦合快照回退后整轮串行重做。单房间候选 `Working` 按值持有房间副本，经 `RoomCtx`（`Rc<RefCell<Working>>`）供整槽宿主的普通 op 取短借用。有 JS 贡献的槽一次进入 VM，组合留在 JS；候选能力在本次调用期间进入 OpState，成功或失败返回后都移除。进入 JS 前不得持候选借用，RefCell 对借用纪律作动态检查。全部规则完成后，候选准备通知和玩家房间集合，确认没有遗留共享句柄，再生成不共享的 `PreparedTick` 供发布。跨线程房间调度按上文资格门受限提供：房间候选由主线程克隆后经共享队列流式逐房派发给结算工作者（克隆与结算重叠），完成消息按房序索引归并，随机数、ID 与事件序不依赖完成顺序；含 JS 宿主贡献槽的轮次强制走串行路径。当前 Mod 范围与失败保证见 [Mod 处理链执行](mod-execution.md)。

世界结算失败时保留旧世界、时间和玩家写回状态，缓存整轮 `RunResult` 与 `TickInput`。重试复用缓存，不再次执行玩家代码；错误的重试请求不清除缓存。引擎结算段失败会进入 `NeedsRecovery`，恢复期间相关修改入口拒绝操作。可通过 `discard_pending_round` 显式放弃缓存和恢复状态。

装配 Mod 的分片在整轮结算返回错误后立即销毁玩法 VM，下次玩家执行或结算前按原包快照与配置重新注册并核验冻结计划。恢复失败仍保留缓存与已提交状态，禁止执行新玩家轮；丢弃缓存也不解除 Mod 恢复门。Mod 持久状态从已提交 namespace 读取，模块全局作为缓存被丢弃。具体机制与未覆盖故障见 [Mod 执行](mod-execution.md#vm-故障恢复)。

Mod 注册与每轮结算具备独立 CPU/墙钟预算和 V8 内存门。结算额度在整轮 Mod 调用间累计，超限作为候选故障，保留玩家结果用于重试；其采样与不可中断 native 边界见 [Mod 资源预算](mod-execution.md#资源预算)。

玩家 JavaScript 全局变量不随世界回退。玩家执行阶段的线程或通信故障会停止新派发，收回已派发任务直到完成或期限到达，并保存已确认的结果，阻止正常运行、外部结算及相关管理修改；不能自动重派。调用方可显式丢弃故障轮，或调用 `rebuild_player_workers` 放弃故障轮并重建全部玩家线程。后者保留已提交世界、内存、segments 和 CPU 桶，保留模块与配置，清空 V8 全局状态；替代线程全部建立后才切换，失败时保留故障门。单纯丢弃不会清空 V8 全局变量或修复死亡线程。命令期限不能强制终止永久卡死的原生 Rust 调用；线程销毁仍需 join，不保证这种故障下重建或析构有界完成。panic、进程崩溃和磁盘恢复不属于普通结算返回错误的保证范围。

以下各节中“必须”“禁止”等表述是完整目标架构的约束。当前具备候选提交与结算失败缓存，并不表示已经具备房间工作者、提交后网络队列或崩溃恢复能力。

## 玩家执行与结算接口

玩家执行、结果分类与候选缓存属于 `kk-runtime`。`RunSpec`、`RunOutcome`、`RunResult` 由该 crate 导出；`PlayerExecutor`/`ThreadExecutor` 只产生候选，不自行推进世界。`EmbedEngine::run_players`（及单玩家包装 `run_player`）是完整玩家轮次入口。

`kk-engine::Engine` 不持有沙箱，也不提供无参数 `tick()`。它提供 `tick_with_intents`、`tick_with_intents_with_input` 和 `tick_with_writebacks`：接收调用方已清洗并绑定身份的指令，后两者使用显式 `TickInput`，最后一项同时接收 `PlayerWriteback`。它们都经过同一套候选阶段和发布点；不会执行玩家代码。内部 `OwnedTickTxn`/`PreparedTick` 保持 crate 内可见。

运行时汇总以注册玩家表的键为准，只保留该玩家的对象、房间、通知、市场和扩展意图，不信任 `RunResult.player` 或回执中的其他玩家键。结算器仍按对象所有权校验动作。玩家级中断、注入失败与基础设施故障沿用正式运行时的分类：基础设施故障阻止整轮提交及自动重派，不会作为空指令成功推进时间。

无 V8 的引擎测试通过显式 `IntentBatch` 回放；`EmbedEngine::settle_external` 也仅结算调用方提供的指令。`EmbedEngine::tick(count)` 是纯世界推进接口。两者遵守运行时的恢复门，但不提供玩家执行或自动写回能力。直接使用引擎的调用方负责保存失败轮的指令、时间与写回候选；需要完整玩家执行语义时使用 `run_players`。

## 目标状态与可见性

以 `V_t` 表示本轮玩家代码开始前**已提交**的世界版本，`P_t` 表示已提交的玩家持久状态
（RawMemory、CPU 桶、账号级数据等）。本轮所有玩家只读同一个 `V_t`，各自运行一次，
输出 `RunResult_t(player)`。房间结算和跨房间阶段产生候选 `V_(t+1)`、`P_(t+1)`；
只有提交点之后它们才对下一轮玩家、查询接口和网络订阅者可见。玩家在本轮看到
`Game.time = t`，提交产生 `V_(t+1)` 后下一轮才看到 `t+1`；半成品不得提前推进时间。

`RunResult` 至少携带玩家身份、运行结局、按房间分组的指令、全局指令、待提交的
RawMemory/CPU 结果及控制台输出。玩家代码抛异常、CPU 超时和桶耗尽属于**有定义的玩家
运行结局**：依官方语义产出该次结果，不自动中止整个 tick。线程失联、协议损坏、
宿主内部错误属于**基础设施故障**，走下文的停顿路径。

## 目标调度阶段

| 阶段 | 输入与完成条件 | 允许的写入 |
|---|---|
| 1. 固定输入 | 固定 `V_t`、`P_t`、玩家名单、活跃房候选与本轮种子 | 只创建本轮工作区 |
| 2. 派发玩家 | 每个注册玩家恰好派发一次；沙箱并发运行 | 各自的私有运行结果 |
| 3. 房间就绪 | 收齐该房间**可能**产生本地指令的全部玩家结果 | 房间私有工作副本 |
| 4. 房间结算 | 输入与语义依赖均就绪；按既定房内阶段序处理，已证独立的工作可重叠 | `RoomPatch`、事件、玩家状态操作 |
| 5. 全局结算 | 全部玩家及房间结果齐备；处理跨房移动、市场、power 等 | 全局候选状态 |
| 6. 验证与提交 | 所有候选通过不变量检查，按确定顺序合并 | 一次切换已提交版本 |
| 7. 发布 | 提交完成 | 控制台、事件、网络变更与检查点任务入队 |

一个玩家可能影响多个房间，但其代码仍只运行一次。玩家完成后，调度器把结果送到
所有相关房间并递减其等待计数。房间依赖集合 `D_t(room)` 必须是**保守上界**，由
已提交世界中的对象归属、视野以及各 API 可指定的目标范围推导；不得仅按该玩家最终提交的
指令倒推，因为那时房间可能已开始结算。

可见 `Room` 上的创建接口只是来源之一，不能据此断言所有房间指令都受视野限制。
上游 `engine/src/game/flags.js` 的 `Flag.remove/setColor` 可以操作不可见房间中的自有旗帜；
`Flag.setPosition` 还可以为创建指令指定新房间，不检查该目标是否在 `Game.rooms` 中。
当前玩家实现见 `prelude/game/sites-flags.js`。这类私有对象或自由目标指令必须单独纳入
依赖分析，或先进入等待全部相关玩家完成的全局阶段，再按已定义顺序与房间结果合并。
市场、跨房传输及 Mod 动作也须逐类说明范围，不能仅从 `Game.rooms` 推导全部依赖。
自由目标可能使某类指令必须等待全部玩家；不能预先承诺依赖集合永不退化为全体玩家。

暂时无法证明依赖集合完整的房间，使用
“等待全部玩家”作为正确性回退。运行结果出现 `D_t` 之外的房间指令时，本轮报
调度不变量错误，禁止提交；不得把它补进一个已启动的房间任务。

空闲房只在官方活跃条件要求时参与结算。唤醒补算必须定义为从 `V_t` 到本轮时间的
确定性状态转移，并与逐 tick 结算跑同一组行为对照；跨房间输入可唤醒目标房。

## 并行结果的确定性合并

> 现行实现注记（2026-10-11）：本节描述目标架构，RoomPatch、依赖推导与全局阶段合并尚未实现。现行并行结算（R09-lite）以"整房候选分块 + 房间序合并 + 锁内可交换累计 + serial_only 串行重做"达到与串行路径逐房间字节级等价（有对照测试），新对象 ID 仍由共享游标在锁内分配，未引入临时 ID。

- 房间工作者只能读 `V_t`、本房候选及由已满足依赖提供的共享候选读面；不得
  直接修改已提交 `World` 或竞争无序的全局 ID/玩家表。输出 `RoomPatch`、
  事件和经证明可合并的 `PlayerOp`；其余共享操作保持参考执行依赖。
- 房间内部仍按官方阶段序、玩家固定序及对象固定序执行。不同房间完成的墙钟顺序
  不进入结果；合并按房间名、房内创建序和已定义的全局阶段序进行。
- 新对象默认保留现有 ID 分配与创建观察顺序；共享 ID 依赖可限制任务并行。
  `(room, local_ordinal)` 临时 ID 只作为未被规则/Mod 观察且可完整重写引用时
  的待验证优化，不能默认用于任意 JS 内容。创建被后续房内步骤读取时，必须
  保留该位置及依赖，不能统一挪到末尾全局阶段。
- 可交换玩家操作可以记录并合并；依赖前房共享写入的读改写在原语义位置有序
  执行，必要时整个房组等待。末尾排序不能修复提前读旧 GCL/配额得出的错误
  分支。只有证明等价的操作才可移到全局阶段。随机协议按[确定性契约](gameplay-determinism.md)
  保留原派生域/消费序，注入流另保留其输入；回放使用固定玩家结果，不重跑玩家随机。

这套合并规则需要与单线程参考执行逐 tick 比对：固定包括 CPU 写回在内的输入后，
世界快照、玩家状态和事件序列必须一致。无共享依赖的房任务可不按房名执行；
存在共享观察顺序时依赖图必须保留它，不能把“最后按房名合并”当作充分条件。

## 失败、重试与持久状态

结算失败时，世界、玩家持久状态、时间、事件和对外输出均不发布。**沙箱已经运行过，
其 V8 全局状态不能视为已回滚。** 因此只允许用缓存的同一批 `RunResult_t` 重试
确定性的结算阶段；不得为重试再次运行玩家代码，也不得启动下一轮。暂时无法恢复
的错误使该 shard 停顿，等待修复或从上一个已提交点恢复。

若玩家线程在结果确认前失联，宿主无法判定代码是否执行，禁止盲目重派同一轮。
应停顿该 shard，按已提交的 `P_t` 重建沙箱并按明确的故障恢复策略处理本轮；
这属于基础设施故障，不伪装成玩家脚本异常。进程崩溃后的恢复能力由
[快照契约](snapshot-contract.md)中的检查点与日志边界决定，不能声称内存回退
自动提供磁盘级原子性。

RawMemory 和 CPU 桶的**宿主持久值**必须暂存到提交点；沙箱内的本轮工作值不得
提前写盘。控制台、事件和网络推送同样缓冲到提交之后。这样失败重试不会重复发送
已对外可见的同一轮结果。若未来允许玩家调用具有外部副作用的 API，必须先定义
幂等键或移入提交后的阶段。

## 调度与提交的验收场景

1. 真实沙箱中的 `move`/`harvest` 指令经过清洗、结算，在下一轮玩家视图中可见；
   测试夹具的显式指令和真实执行候选走同一条结算入口。
2. 一个玩家影响两房、两玩家影响一房、无关房先完成三种情况，均与串行参考结果一致；
   故意打乱玩家完成顺序，结果不变。
3. 在第二个房间注入结算失败：世界、玩家持久值、时间和对外事件不变；重试只消费
   已缓存的运行结果，玩家代码执行次数仍为一次。
4. 缺失玩家结果、越权身份、依赖集合遗漏和跨房间 ID 引用都以可归因的错误拒绝提交。
5. 测量重叠收益时报告玩家线程数、活跃房数和机器核数；“最慢房间决定 tick 时长”
   仅是理想上界附近的假设，正式结果按[性能验收](performance-acceptance.md)测量。
