## 状态与可见性

以 `V_t` 表示本轮玩家代码开始前**已提交**的世界版本，`P_t` 表示已提交的玩家持久状态
（RawMemory、CPU 桶、账号级数据等）。本轮所有玩家只读同一个 `V_t`，各自运行一次，
输出 `RunResult_t(player)`。房间结算和跨房间阶段产生候选 `V_(t+1)`、`P_(t+1)`；
只有提交点之后它们才对下一轮玩家、查询接口和网络订阅者可见。玩家在本轮看到
`Game.time = t`，提交产生 `V_(t+1)` 后下一轮才看到 `t+1`；半成品不得提前推进时间。

`RunResult` 至少携带玩家身份、运行结局、按房间分组的指令、全局指令、待提交的
RawMemory/CPU 结果及控制台输出。玩家代码抛异常、CPU 超时和桶耗尽属于**有定义的玩家
运行结局**：依官方语义产出该次结果，不自动中止整个 tick。线程失联、协议损坏、
宿主内部错误属于**基础设施故障**，走下文的停顿路径。

## 调度阶段

| 阶段 | 输入与完成条件 | 允许的写入 |
|---|---|
| 1. 固定输入 | 固定 `V_t`、`P_t`、玩家名单、活跃房候选与本轮种子 | 只创建本轮工作区 |
| 2. 派发玩家 | 每个注册玩家恰好派发一次；沙箱并发运行 | 各自的私有运行结果 |
| 3. 房间就绪 | 收齐该房间**可能**产生本地指令的全部玩家结果 | 房间私有工作副本 |
| 4. 房间结算 | 按官方房间内阶段序处理；不同就绪房可重叠执行 | `RoomPatch`、事件、玩家状态操作 |
| 5. 全局结算 | 全部玩家及房间结果齐备；处理跨房移动、市场、power 等 | 全局候选状态 |
| 6. 验证与提交 | 所有候选通过不变量检查，按确定顺序合并 | 一次切换已提交版本 |
| 7. 发布 | 提交完成 | 控制台、事件、网络变更与检查点任务入队 |

一个玩家可能影响多个房间，但其代码仍只运行一次。玩家完成后，调度器把结果送到
所有相关房间并递减其等待计数。房间依赖集合 `D_t(room)` 必须是**保守上界**，由
已提交世界中的对象归属、视野和可执行的房间级 API 推导；不得仅按该玩家最终提交的
指令倒推，因为那时房间可能已开始结算。这个推导在官方语义下是封闭的：`Game.rooms`
只从按视野过滤的 `runtimeData.rooms` 注册 `Room` 实例（官方 game.js:218-220），
room 级 intent（createFlag/createConstructionSite 等）在官方 API 面上只能经可见
Room 对象触达——不存在"向未见房间任意发指令"的官方路径，因此依赖集合不会退化为
"全体玩家"。玩家 API 层若引入新的跨房入口，须先证明其视野门控再纳入推导。
暂时无法证明依赖集合完整的房间，使用
“等待全部玩家”作为正确性回退。运行结果出现 `D_t` 之外的房间指令时，本轮报
调度不变量错误，禁止提交；不得把它补进一个已启动的房间任务。

空闲房只在官方活跃条件要求时参与结算。唤醒补算必须定义为从 `V_t` 到本轮时间的
确定性状态转移，并与逐 tick 结算跑同一组行为对照；跨房间输入可唤醒目标房。

## 并行结果的确定性合并

- 房间工作者只能读 `V_t` 与本房工作副本；不得直接修改已提交 `World`、全局 ID
  分配器或玩家表。它们输出 `RoomPatch`、`PlayerOp`、事件和本房临时对象 ID。
- 房间内部仍按官方阶段序、玩家固定序及对象固定序执行。不同房间完成的墙钟顺序
  不进入结果；合并按房间名、房内创建序和已定义的全局阶段序进行。
- 新对象在工作阶段使用 `(room, local_ordinal)` 临时 ID。全房间成功后按固定顺序
  分配全局单调 ID，并重写对象引用和事件中的临时 ID。若某规则必须在同一轮依据
  跨房最终 ID 或玩家全局状态作判断，就把该规则移至全局阶段，不能让工作者竞争
  全局锁来决定语义。
- 玩家状态操作由房间工作者记录、在固定顺序下合并。不可交换的操作及依赖最新
  全局状态的检查在全局阶段串行执行。引擎自己的随机数从记录在输入中的种子派生；
  回放以已收集的指令和运行结果为输入，不重新执行玩家的 `Math.random()`。

这套合并规则需要与单线程参考执行逐 tick 比对：相同输入的世界快照、玩家状态和
事件序列必须一致。房间名排序是**合并规则**，不要求任务按房间名串行运行。

## 失败、重试与持久状态

结算失败时，世界、玩家持久状态、时间、事件和对外输出均不发布。**沙箱已经运行过，
其 V8 全局状态不能视为已回滚。** 因此只允许用缓存的同一批 `RunResult_t` 重试
确定性的结算阶段；不得为重试再次运行玩家代码，也不得启动下一轮。暂时无法恢复
的错误使该 shard 停顿，等待修复或从上一个已提交点恢复。

若玩家线程在结果确认前失联，宿主无法判定代码是否执行，禁止盲目重派同一轮。
应停顿该 shard，按已提交的 `P_t` 重建沙箱并按明确的故障恢复策略处理本轮；
这属于基础设施故障，不伪装成玩家脚本异常。进程崩溃后的恢复能力由
[快照契约](snapshot-contract.md)中的检查点与日志边界决定，不能声称内存回退
自动提供磁盘级原子性。

RawMemory 和 CPU 桶的**宿主持久值**必须暂存到提交点；沙箱内的本轮工作值不得
提前写盘。控制台、事件和网络推送同样缓冲到提交之后。这样失败重试不会重复发送
已对外可见的同一轮结果。若未来允许玩家调用具有外部副作用的 API，必须先定义
幂等键或移入提交后的阶段。

## 进入 M2 的验收场景

1. 真实沙箱中的 `move`/`harvest` 指令经过清洗、结算，在下一轮玩家视图中可见；
   假沙箱和真实沙箱走同一条结算入口。
2. 一个玩家影响两房、两玩家影响一房、无关房先完成三种情况，均与串行参考结果一致；
   故意打乱玩家完成顺序，结果不变。
3. 在第二个房间注入结算失败：世界、玩家持久值、时间和对外事件不变；重试只消费
   已缓存的运行结果，玩家代码执行次数仍为一次。
4. 缺失玩家结果、越权身份、依赖集合遗漏和跨房间 ID 引用都以可归因的错误拒绝提交。
5. 测量重叠收益时报告玩家线程数、活跃房数和机器核数；“最慢房间决定 tick 时长”
   仅是理想上界附近的假设，正式结果按[性能验收](performance-acceptance.md)测量。
