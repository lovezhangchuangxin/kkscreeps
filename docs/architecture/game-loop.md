# 游戏循环（Tick Pipeline）

游戏以固定节拍运转，一个节拍叫一个 **tick**。官方 MMO 服务器一个 tick 约 2~5 秒（视分片与负载），私服约 1 秒起步。本文说明目标流水线；具体的依赖、提交与失败语义见 [tick 契约](tick-contract.md)。M1 当前仍是同步收集与串行逐房结算。

## 一次 tick 的完整流程

```
┌─ ① 固定上一轮已提交的世界与玩家状态，准备本轮临时数据区
│
├─ ② 玩家代码阶段（每玩家运行一次，可并发）
│    玩家返回指令、Memory/CPU 结果；房间等待其保守依赖集合内的玩家
│
├─ ③ 房间结算阶段（与 ② 交叠进行）
│    房间依赖收齐后，以工作副本按官方阶段序结算
│    产出候选房间状态、玩家状态操作与事件
│
├─ ④ 跨房间阶段：等所有房间结算完
│    爬爬虫（creep，玩家代码控制的基本游戏单位）跨房间移动的落地、市场成交、
│    power（游戏中的高级资源与技能系统）结算
│
└─ ⑤ 全部验证成功后一次提交时间和状态，再发布变更集；空闲房间进入休眠
```

## 关键设计一：不等全部玩家，按房间流水线推进

官方的做法是：**所有**玩家的代码跑完 → 才开始处理**任何**房间。这意味着只要有一个玩家的代码慢，所有房间都在干等（官方引擎作者本人在他的重写项目里点名批评过这一点）。

目标做法：每个玩家代码只运行一次；房间等待其**可能受影响的玩家集合**全部返回后即可结算。依赖集合必须是保守上界，无法证明完整时该房间退回等待全部玩家。这样可以重叠无关房间的结算与尚未完成的玩家运行。收益取决于玩家/房间依赖图、核数和资源争用；“接近最慢房间耗时”只是理想情形的推断，按[性能验收](performance-acceptance.md)作端到端测量。官方的 runner 其实有 2~4 路并发，并非严格串行求和，但全局等待仍是可优化点。

一个房间里有多个玩家时，他们的代码实例可并行运行；房内指令按固定玩家序结算。跨房间的 ID 与玩家状态在提交阶段按固定顺序合并，详见 [tick 契约](tick-contract.md)。

没有玩家活动的房间（休眠房间）不参与逐房流水线。是否"有活动"的判定以官方行为为准：房间内存在玩家所属对象，或本 tick 收到了该房间相关指令等情况。休眠不等于时间冻结；唤醒时的资源重生、结构衰减等补算必须与逐 tick 行为对照验证，不能仅凭时间差近似。

## 关键设计二：确定性（同样的输入，同样的结果）

并行处理多个房间时，如果处理顺序每次不同，结果可能不同，回放功能也会失效。所以：

- **房间之间的结算顺序固定**（按房间名排序），并行只用于互不影响的房间内部计算，汇总时按固定顺序合并；
- 所有随机数来自带种子的随机数发生器（种子保存在世界数据里）；
- 数据结构的遍历顺序固定（不用无序哈希表的遍历序）。

这样"从任意一个历史时间点 + 当时的玩家指令序列"可以精确重放出之后的所有状态——回放（replay）功能就是它的直接应用。玩家代码里的 `Math.random()` 保持官方行为（不纳入引擎的种子化管理），确定的是我们引擎自己的结算。

## 房间结算内部：用索引代替全表扫描

官方引擎在房间结算时有大量"按坐标找对象"的操作（判断移动障碍、落地格、传送门等），实现方式是把房间里全部对象从头到尾扫一遍——一个 50 爬爬虫（creep）的房间，一个 tick 要做约 8 万次这样的逐个检查（实测约 3.7 毫秒）。

目标做法：为房间维护 50×50 的格子索引（每个格子记录"这格上有哪些对象"），查询从"扫全表"变成"查一格"。孤立查询基准从 3.7 毫秒降到 0.043 毫秒（约 80 倍）；完整 tick 还需计入建索引、复制与维护成本。M1 在每次结算时重建索引，是否改为随快照保留由端到端基准决定。

其他同类的替换：对象按类型分桶存放（结算时按类型批量处理，不用反复判断类型字符串）；衰减类结算（道路磨损、 rampart 衰减等）用"到期时间堆"只处理到期的对象，而不是每 tick 遍历全部。

## 结算的失败处理：失败即回退

官方在部分房间结算错误后可能继续推进。我们的目标是**候选状态未全部成功就不提交整个 tick**，避免同一时间点上只推进部分房间。工作副本允许丢弃半成品，但复制、缓存与失败恢复均有成本；玩家沙箱已经执行时也不能假定其状态随房间回滚。重试只能复用已收集的同一批运行结果，具体故障分流见 [tick 契约](tick-contract.md)。这项差异须继续按[兼容灰区](../designs/compatibility.md)管理。

## tick 速率：跟随负载 + 硬上限保护

默认跟随负载（官方行为：忙时 tick 自然拉长）。但设保护上限：超过阈值时丢弃最慢玩家的执行，宁可让个别玩家跳一 tick 也保住服务器整体节拍。速率运行时可调（对应官方 CLI 的 setTickDuration）。

## 引擎的执行模型

目标执行模型是同步主循环协调玩家线程与房间任务，房间结算可用 rayon 数据并行，磁盘检查点与网络推送在提交后后台执行。游戏规则本身保持同步、确定性；M1 的 `Engine::tick` 尚未并行化。任务完成顺序不参与语义，合并按固定顺序执行。

## 玩家指令（intent）的流转

玩家代码不直接修改游戏状态，只产生"指令"（比如 `creep.move(TOP)`、`spawn.spawnCreep(...)`）。指令的完整路径：

1. 玩家在沙箱内调用游戏 API → 沙箱内的收集器把指令记下来（同一种指令只记最后一次，每条指令计入 0.2 的 CPU 计费——与官方一致。这里的"CPU"是玩家每 tick 分到的计算配额货币，约等于毫秒，细则见 [sandbox.md](sandbox.md) 的预算桶一节）；
2. tick 末尾，沙箱把本 tick 的全部指令一次性传给引擎（二进制编码，不走 JSON 文本）；
3. 引擎在校验字段合法性后，按官方相同的优先级规则结算（同一爬爬虫的冲突动作按优先级图裁决，被覆盖的动作仍返回成功码——官方语义）；
4. 结算结果写进新的房间快照，同时产出"本 tick 变更集"。

引擎在结算前会独立校验每条指令的字段（官方 `system.js` 的白名单规则），沙箱传来的数据一律视为不可信。
