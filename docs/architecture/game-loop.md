# 游戏循环（Tick Pipeline）

游戏以固定节拍运转，一个节拍叫一个 **tick**。官方 MMO 服务器一个 tick 约 2~5 秒（视分片与负载），私服约 1 秒起步；我们的目标是让它只受"最慢的那个房间"限制（此为设计目标，标注为推断，前提见下文"关键设计一"）。本文描述一个 tick 内部发生什么。

## 一次 tick 的完整流程

```
┌─ ① tick 开始：游戏时间 +1，准备本 tick 的临时数据区
│
├─ ② 玩家代码阶段（每个房间独立推进，互不等待）
│    对每个活跃房间：
│      等这个房间里的所有玩家代码跑完
│      → 立刻进入这个房间的结算（不等其他房间）
│
├─ ③ 房间结算阶段（与 ② 交叠进行）
│    按固定顺序执行：NPC 行为 → 玩家指令 → 移动仲裁 → 逐对象结算 → 事件记录
│    产出：新的房间快照 + 本 tick 的变更集
│
├─ ④ 跨房间阶段：等所有房间结算完
│    爬爬虫（creep，玩家代码控制的基本游戏单位）跨房间移动的落地、市场成交、
│    power（游戏中的高级资源与技能系统）结算
│
└─ ⑤ tick 结束：发布变更集给网络层推送给客户端；空闲房间进入休眠
```

## 关键设计一：不等全部玩家，按房间流水线推进

官方的做法是：**所有**玩家的代码跑完 → 才开始处理**任何**房间。这意味着只要有一个玩家的代码慢，所有房间都在干等（官方引擎作者本人在他的重写项目里点名批评过这一点）。

我们的做法：给每个房间配一个计数器。这个房间的最后一个玩家交回指令时，计数器归零，该房间立刻进入结算。**预期** tick 总时长从"所有玩家耗时之和 + 所有房间结算之和"变成"大致等于最慢的一个房间的完整流程"（此收益在调研中标注为推断；它的前提是玩家代码真正并发运行——即沙箱采用"一个玩家实例绑一个线程"的模型，该模型待 M0 原型验证）。官方的 runner 其实有 2~4 路并发，并非严格串行求和，但"全体玩家跑完才开始处理房间"的全局等待是实打实的。

一个房间里有多个玩家时：他们的代码实例并行运行；指令的结算顺序按固定规则（玩家标识排序）保证确定性。具体调度细节属于 M1 的设计内容。

没有玩家活动的房间（休眠房间）不参与上述流程。是否"有活动"的判定沿用官方口径：房间内存在玩家所属的对象，或本 tick 收到了该房间相关的指令（细化规则在 M1 定）。休眠不等于时间冻结——房间被唤醒时要按离线时长一次性补算资源重生、结构衰减等（官方的定时任务就是干这个的，我们做得更省：只在唤醒时补算，而不是每 20 秒唤醒全部房间）。

## 关键设计二：确定性（同样的输入，同样的结果）

并行处理多个房间时，如果处理顺序每次不同，结果可能不同，回放功能也会失效。所以：

- **房间之间的结算顺序固定**（按房间名排序），并行只用于互不影响的房间内部计算，汇总时按固定顺序合并；
- 所有随机数来自带种子的随机数发生器（种子保存在世界数据里）；
- 数据结构的遍历顺序固定（不用无序哈希表的遍历序）。

这样"从任意一个历史时间点 + 当时的玩家指令序列"可以精确重放出之后的所有状态——回放（replay）功能就是它的直接应用。玩家代码里的 `Math.random()` 保持官方行为（不纳入引擎的种子化管理），确定的是我们引擎自己的结算。

## 房间结算内部：用索引代替全表扫描

官方引擎在房间结算时有大量"按坐标找对象"的操作（判断移动障碍、落地格、传送门等），实现方式是把房间里全部对象从头到尾扫一遍——一个 50 爬爬虫（creep）的房间，一个 tick 要做约 8 万次这样的逐个检查（实测约 3.7 毫秒）。

我们的做法：房间加载时建一个 50×50 的格子索引（每个格子记录"这格上有哪些对象"），查询从"扫全表"变成"查一格"。实测同样的查询从 3.7 毫秒降到 0.043 毫秒（约 80 倍）。对象只有在移动结算这一处集中改坐标，索引随之增量更新，维护成本很低。

其他同类的替换：对象按类型分桶存放（结算时按类型批量处理，不用反复判断类型字符串）；衰减类结算（道路磨损、 rampart 衰减等）用"到期时间堆"只处理到期的对象，而不是每 tick 遍历全部。

## 结算的失败处理：失败即回退

官方的做法很糟：房间结算出错只打一行日志，房间照常标记完成，数据可能处于半写状态。我们利用双缓冲天然回退：**结算失败就丢弃当前槽的半成品，房间保持上一 tick 的状态**，错误上报管理端，下一 tick 重试或冻结该房间。这是零额外成本的可靠性升级，玩家不可感知。

## tick 速率：跟随负载 + 硬上限保护

默认跟随负载（官方行为：忙时 tick 自然拉长）。但设保护上限：超过阈值时丢弃最慢玩家的执行，宁可让个别玩家跳一 tick 也保住服务器整体节拍。速率运行时可调（对应官方 CLI 的 setTickDuration）。

## 引擎的执行模型

tick 主循环用**同步代码**驱动（tokio 单线程运行时承载，只为满足 deno_core 的事件循环要求，引擎逻辑本身不写异步）；房间结算用 **rayon 线程池做数据并行**；磁盘检查点与网络推送放后台线程。游戏 tick 是批处理而非高并发 IO，不把引擎内部做成 async/await 风格——那会让确定性顺序复杂化而收益很小。

## 玩家指令（intent）的流转

玩家代码不直接修改游戏状态，只产生"指令"（比如 `creep.move(TOP)`、`spawn.spawnCreep(...)`）。指令的完整路径：

1. 玩家在沙箱内调用游戏 API → 沙箱内的收集器把指令记下来（同一种指令只记最后一次，每条指令计入 0.2 的 CPU 计费——与官方一致。这里的"CPU"是玩家每 tick 分到的计算配额货币，约等于毫秒，细则见 [sandbox.md](sandbox.md) 的预算桶一节）；
2. tick 末尾，沙箱把本 tick 的全部指令一次性传给引擎（二进制编码，不走 JSON 文本）；
3. 引擎在校验字段合法性后，按官方相同的优先级规则结算（同一爬爬虫的冲突动作按优先级图裁决，被覆盖的动作仍返回成功码——官方语义）；
4. 结算结果写进新的房间快照，同时产出"本 tick 变更集"。

引擎在结算前会独立校验每条指令的字段（官方 `system.js` 的白名单规则），沙箱传来的数据一律视为不可信。
